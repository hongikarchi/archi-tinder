# 공모전 팀빌딩 — 찜 기반 설계

**작성** 2026-09-17 · **상태** 방향 확정, 구현 미착수 · **선행** `2026-08-20-personality-discovery-design.md` §10 (Defer 해제)

---

## 1. 출발점과 기각된 전제

`personality-discovery-design.md` §10은 "팀원 추천 v2"를 Defer하며 이렇게 적었다:

> 공모전 역할별 요구 스킬 + 다축 상호보완 최적화 로직 필요 / v1 발견 피드 피드백 없이 설계 시 낭비 큼

이번 논의에서 **그 접근 자체가 틀렸다**는 결론에 도달했다. 문제는 최적화 로직의 정교함이 아니라 **수요의 존재**였다.

### 기각: "낯선 사람과 팀을 매칭해준다"

user 지적 — *"건축 공모전은 보통 잘 맞는 친구랑 하지 않나"*. 검토 결과 타당하다:

- 공모전은 몇 주~몇 달 밤새는 고강도 협업. 실력·성실도·마감 감각을 모르는 사람과 시작하는 건 위험이 큼
- 그래서 대부분 같은 스튜디오, 이미 아는 사이에서 팀이 짜인다
- **"취향이 비슷하다"는 팀을 짤 이유로 약하다**
- 공모전은 1년에 몇 번 → 그 순간에만 쓰이는 기능은 앱을 활성화시키지 못한다 (나머지 기간 死)

빈 곳이 없진 않다(편입생·유학생·한 자리 부족·타학교 협업·졸업생). 그러나 **얇다.** 메인 기능으로 놓으면 앱이 돌지 않는다.

### 페르소나 우선순위 재정의 (기록)

`CLAUDE.md` Product Constitution은 `P1(회사→구직자) > P2(사람↔사람)`이며 "충돌 시 P1이 이긴다 — **유저가 재정의하지 않는 한**"이다.

**2026-09-17 user 결정: P2 우선.** 이 문서의 설계는 그 재정의 위에 선다.

## 2. 핵심 전환

> 앱이 팀을 **만들어주려** 하지 말고, 공모전 자체를 **평소에 볼 거리**로 만든다.

전환의 근거는 동기 신호의 세기 차이다:

| 신호 | 세기 | 비고 |
|---|---|---|
| 취향이 비슷하다 | 약함 | 팀을 짤 이유가 되지 못함 |
| **같은 공모전을 하고 싶어한다** | **강함** | 의도가 이미 일치 |

찜은 이 강한 신호를 **부담 0의 행동**으로 수집한다. 팀 짤 생각이 없어도 누른다.

---

## 3. 흐름

```
운영자가 공모전 등록 (이름 · 주제 · 마감 · 권장 인원)
   ↓
유저가 "관심" 찜 — 부담 0
   ↓
같은 공모전을 찜한 사람 목록 + 취향 겹침 표시
   ("이 공모전 찜한 사람 중 당신과 1·2축이 보완되는 3명")
   ↓
팀 만들기 = ① 친구 초대(정상 경로)  또는  ② 찜한 사람에게 제안
   ↓
팀 진단 — 팀 전체의 축 구성 (공유 가능한 물건)
   ↓
빈 자리가 있으면 "1자리 남음" → 이때만 매칭 발동
```

### 두 문제를 푸는 방식

**저빈도 → 고빈도**: 팀을 안 짜도 공모전 목록·찜·마감 카운트다운이 매일 볼 거리가 된다. 팀빌딩은 그 위에서 가끔 일어나는 사건일 뿐, 기능의 전부가 아니다.

**"친구랑 한다"를 거스르지 않음**: 앱은 낯선 사람과의 팀 결성을 강요하지 않는다. **친구를 초대해 팀을 등록하는 것이 정상 경로**이고, 매칭은 **한 자리가 빌 때만** 작동한다. 현실에 올라타면서 얇은 빈 곳(한 자리 부족·편입생·타학교)을 자연스럽게 흡수한다.

## 4. 축별 계산 — 발견 피드와 정반대인 지점

발견 피드는 **가까운 사람**을 보여준다(`_euclidean`). 팀은 축마다 다르게 봐야 한다.

| 축 | 양극 | 팀에서 | 이유 |
|---|---|---|---|
| 1 작업 방식 | 개념 ↔ 실무 | **보완**(멀수록 좋음) | 컨셉 잡는 사람 + 도면 그리는 사람 |
| 2 역할 성향 | 리더 ↔ 서포터 | **보완**(멀수록 좋음) | 리더만 셋이면 팀이 깨진다 |
| 3 협업 방식 | 협업 ↔ 독립 | **일치**(가까울수록 좋음) | 협업형·독립형이 섞이면 갈등 |
| 4 접근 태도 | 혁신 ↔ 전통 | **일치**(가까울수록 좋음) | 안이 모이지 않는다 |
| 5 결정 속도 | 신중 ↔ 즉흥 | 보너스 | 그래프 모양에만 반영 |

같은 벡터를 쓰되 **거리 함수가 축마다 부호가 다르다.** 발견 피드의 `_euclidean`을 그대로 쓸 수 없고, 가중 합성이 필요하다.

> **미결**: 1·2축 보완과 3·4축 일치를 어떤 비율로 합칠지. v1 데이터 축적 후 결정. 초기에는 단순 평균으로 두고 실제 팀 결성 결과로 보정한다.

## 5. 유니크 · 키치가 나오는 지점

- **팀 진단** — *"우리 팀은 개념형 2 + 실무형 1, 리더가 둘이라 위험"*. 페르소나 리포트가 1인용 물건이었다면 이것은 **팀용 물건**이고, 스크린샷해서 공유하고 싶어진다
- **찜한 사람 수** — *"이 공모전, 당신 말고 23명이 노리는 중"*. 경쟁 심리가 자연스러운 긴장을 만든다
- **한 자리 남음** — 희소성이 진짜다. 억지로 만든 배지가 아니라 실제 팀 구성에서 파생된다

## 6. 데이터 모델

신규 **4종**. 기존 자산을 최대한 재사용한다.

> 초안에서는 3종으로 적었으나, 구체화 과정에서 **초대에 상태가 필요**하다는 점이 드러나 `TeamInvite`가 추가됐다(아래 참조).

### 6-1. `Competition` — 운영자 등록

| 필드 | 비고 |
|---|---|
| `title` · `organizer` · `theme` | 기본 정보 |
| **`deadline`** | `db_index=True`. 마감 정렬·카운트다운의 핵심이라 인덱스 필수 |
| `team_size_min` / `team_size_max` | "한 자리 남음" 계산의 근거 |
| `official_url` | 공식 요강 링크 |
| `is_published` | 운영자가 준비 중인 행을 숨길 수 있게 |
| `interest_count` | 찜 수. 시그널로 유지(6-2) |

유저 입력이 없으므로 데이터가 깨끗하고 중복이 없다.

### 6-2. `CompetitionInterest` (찜) — `Reaction`과 완전히 동형

`social.Reaction`을 그대로 베껴 쓸 수 있다:

- `user` FK + `competition` FK + `created_at(db_index)`
- `unique_together = [('user', 'competition')]`
- `Competition.interest_count`를 `post_save` / `post_delete` 시그널로 유지
- 증가는 `F('interest_count') + 1`, 감소는 `Greatest(F(...) - 1, 0)` — 동시 삭제·카운터 드리프트로 음수가 되는 것을 막는 기존 방어를 그대로 가져온다

### 6-3. `Team`

| 필드 | 비고 |
|---|---|
| `competition` FK · `name` · `owner`(팀장) | |
| `capacity` | 기본값은 `competition.team_size_max`이되 팀이 자체 결정 가능 |
| `is_recruiting` | "정원은 안 찼지만 더 안 받음"을 표현하기 위해서만 존재 |
| `member_count` | 시그널로 유지 |

> **빈 자리는 저장하지 않고 파생시킨다** (`capacity - member_count`).
> 같은 사실을 두 군데 저장하면 반드시 어긋난다.

### 6-4. `TeamInvite` — 초대 (신규, 4번째)

`team` · `invitee` · `status`(`pending` / `accepted` / `declined`) · `created_at`

**`Notification`으로 대신할 수 없다.** 알림 모델에는 *읽음* 상태만 있고 *수락/거절* 상태가 없다. 알림은 "초대가 왔다"를 알리는 용도로만 쓰고(`TYPE_CHOICES`에 타입 추가), 초대의 생사는 이 모델이 관리한다.

### 6-5. 넣지 않는 것

**`role`(역할) 필드** — §3에서 기각한 B안(역할 슬롯 매칭)과 같은 이유다. 실제 공모전 팀은 역할이 그렇게 깔끔하게 나뉘지 않으며, 과한 형식화는 입력 부담만 만든다.

**유저 팔로우** — 재도입 가능하나(2026-06-14 제거는 방향 전환이었을 뿐) 이 설계에는 불필요하다. 찜이 약한 연결 층을 대신한다.

## 7. 화면

새 탭을 만들지 않는다. TabBar 3개(디스커버리 / Taste / 프로필) 구조를 건드리지 않고, **Social 탭 안에서 `[사람] [공모전]` 세그먼트**로 나눈다. Social 탭은 현재 `/people`이며 `/assessment`도 여기 속한다.

### 7-1. 공모전 목록 — 마감 임박순

```
┌──────────────────────────────┐
│ 2026 대학생 건축대전            │
│ 대한건축사협회                  │
│ D-3 · 23명 관심 · 2팀 모집중    │
└──────────────────────────────┘
```

마감이 임박한 순서가 기본. 저빈도 문제를 푸는 화면이므로 **팀을 짤 생각이 없어도 볼 만해야** 한다.

### 7-2. 공모전 상세 — 이 설계의 핵심 화면

- **상단**: 제목 · 주최 · **D-n** · 요강 링크
- **[관심] 찜 토글** — 큰 버튼. 부담 0의 행동이므로 가장 누르기 쉬운 자리
- **섹션 A — 이 공모전을 찜한 사람**: 취향 겹침 순 정렬. `PersonCard`를 그대로 재사용하고 `"1·2축 보완"` 배지만 얹는다
- **섹션 B — 모집 중인 팀**: `"1자리 남음"`
- **[팀 만들기] CTA**

찜 → 같은 의도를 가진 사람 발견 → 팀으로 이어지는 전환이 이 한 화면에서 일어난다.

### 7-3. 팀 상세

- **팀 진단** — 오각형에 멤버 N명을 겹쳐 그리고, `"개념형 2 · 실무형 1, 리더가 둘이라 위험"` 같은 문장을 붙인다. 이 화면의 주인공이며 §5의 공유 동기가 나오는 지점
- 멤버 목록 · 빈 자리 → **[초대하기]** (팀장만)
- 나에게 온 초대라면 **[수락] [거절]**

### 7-4. 팀 만들기 시트

팀 이름 · 정원 · 초대할 사람 선택(찜한 사람 중 또는 검색). `SaveBoardModal`의 바텀시트 패턴을 재사용한다.

## 8. 재사용 vs 신규

| 재사용 | 신규 |
|---|---|
| `PersonCard` (찜한 사람 목록) | **`PentagonChart` N명 확장** — 현재 `myVector` + `theirVector` **2명까지만** 지원. 팀 진단은 3~4명이라 확장 필요. 구현 시 놓치기 쉬운 지점 |
| `SaveBoardModal` 바텀시트 패턴 | 팀 진단 문장 생성 |
| `Reaction` 시그널 패턴 (6-2) | 축 가중 합성 (§4) |
| `Notification` (타입만 추가) | 관리 커맨드 `register_competition` (8-1) |
| `_get_vector` / `_axis_distance` | 화면 4종 |

### 8-1. 운영 도구는 admin이 아니라 관리 커맨드

**프로덕션에는 Django admin이 없다**:

```python
if settings.DEBUG:                      # config/urls.py:14
    urlpatterns += [path('admin/', admin.site.urls)]
```

admin은 개발 환경에서만 열린다. 따라서 "운영자가 미리 등록"을 admin 화면으로 하려던 계획은 프로덕션에서 성립하지 않는다.

이 저장소의 운영 작업 선례는 **관리 커맨드**다 — `seed_discovery` · `sync_offices` · `purge_legacy_projects`. 공모전 등록도 같은 방식을 따른다.

## 9. 거절 처리 (미결)

팀빌딩은 필연적으로 누군가 떨어진다. 건축 학과 커뮤니티는 좁아 서로 얼굴을 아는 경우가 많다.

논의 중 user가 전제 자체를 재검토하며 이 항목은 결론에 이르지 못했다. 후보:

- 지원자 명단은 팀장만 보고, 탈락 시 알림 없이 조용히 마감 (부담 최소)
- 지원자 **수**만 공개하고 명단은 비공개 (활기 ↔ 경쟁률 부담)
- 양방향 합의만 (지원 개념 없음 — 상처는 없으나 속도가 느림)

**찜 중심 설계에서는 이 문제가 완화된다.** 찜은 거절 대상이 아니고, 제안은 팀장이 먼저 보내는 구조이기 때문이다. 구현 시 재검토.

## 11. 구현 전 확인

이 문서는 **방향 합의**까지다. 착수 전에 필요한 것:

1. **발견 피드 v1의 실사용 데이터** — 선행 문서 §10의 Defer 사유가 아직 완전히 해소되지 않았다. 현재 발견 피드는 실사용자 중 노출 조건을 만족하는 사람이 거의 없다(`FRONT-PEOPLE-CARD-2` 참고)
2. **운영자가 실제로 공모전을 등록·관리할 의지** — 등록 경로 자체는 §8-1에서 정해졌다
3. **§10 미결 중 최소한 축 가중치** — 나머지(거절 처리·소통 수단·수명 관리)는 구현 중 결정 가능하나 축 가중치는 매칭 품질의 근간이라 선행되어야 한다
