# 성향 기반 유저 발견 (Personality Discovery) 설계 문서

**작성일**: 2026-08-20  
**상태**: 브레인스토밍 확정 — 구현 플래닝 전  
**범위**: P2 협업/팀빌딩 발견 기능 — 연애 매칭 아님

---

## 1. 핵심 전제

- **목적**: 건축 성향이 비슷하거나 상반된 유저를 발견해 공모전 팀빌딩 / 질문/대화 연결
- **연애·낭만 맥락 완전 배제** (Product Constitution P2 원칙)
- 발견은 유저 간 "미적 취향 + 협업 성향" 매칭이며, 실물 프로젝트 협력이 목표

## 2. 성향 축 구조 (확정)

### 2-1. 4+1 축 모델

| 번호 | 축 이름 | 양극 | 코드 영향 |
|---|---|---|---|
| 1 | 작업 방식 | 개념 ↔ 실무 | ✅ 코어 |
| 2 | 역할 성향 | 리더 ↔ 서포터 | ✅ 코어 |
| 3 | 협업 방식 | 협업 ↔ 독립 | ✅ 코어 |
| 4 | 접근 태도 | 혁신 ↔ 전통 | ✅ 코어 |
| 5 | 결정 속도 | 신중 ↔ 즉흥 | ❌ 보너스 (그래프 모양만) |

### 2-2. 16유형 코드

코어 4축의 이진 조합(2⁴ = 16). 각 축에서 중심값(0)은 가까운 쪽으로 반올림.  
**타이브레이크**: 4문항 평균이 정확히 0.0인 경우 음수 방향(-) 쪽으로 배정 (실무/서포터/독립/전통 극). 4문항 평균은 0.25 단위로만 떨어지므로 정확히 0.0이 되는 패턴(-1,+1,0,0 등)은 실제로 발생할 수 있다.  
보너스 5축(신중↔즉흥)은 16Personalities의 Assertive/Turbulent 접미사 구조와 동일하게 **코드에 영향 없이** 5각형 그래프 모양에만 반영.

### 2-3. 축값 표현

- 각 축: **-1.0 ~ +1.0** (float, 양극 bounded)
- 산출: 해당 축 문항 응답 평균 (Likert -2~+2) / 2 로 정규화
- 거리 계산: 5차원 유클리드 거리 (발견 추천 로직용)

## 3. 성향 진단 문항 설계 (확정)

### 3-1. 문항 구성

| 축 | 문항 수 | 비고 |
|---|---|---|
| 코어 4축 × 4문항 | 16문항 | 축당 4문항 |
| 보너스 축 × 4문항 | 4문항 | 결과에 보조 반영 |
| **합계** | **20문항** | |

### 3-2. 응답 형식

**Likert 5점 척도**

| 점수 | 레이블 |
|---|---|
| -2 | 전혀 아님 |
| -1 | 아닌 편 |
| 0 | 보통 |
| +1 | 맞는 편 |
| +2 | 매우 맞음 |

- 중간 성향(중립형) 포착 가능
- 극단 유형이 아닌 실제 스펙트럼 분포 반영

### 3-3. 문항 텍스트 (미결, 별도 작업)

실제 20문항 텍스트는 별도 작업에서 작성 예정. 설계 원칙:
- 건축/디자인 맥락 상황 제시 ("팀 프로젝트 중 의견 충돌 시…")
- 사회적 바람직성 편향 최소화 (정답 없는 상황 설정)
- 역방향 문항(reverse-coded) 최소 2문항/축 포함

## 4. 발견(Discovery) UX (확정)

### 4-1. 카드 피드

- 각 카드: 프로필 사진 + 이름 + 유형 코드 + **미니 5각형 그래프**
- 나와 가장 차이나는 축 하나만 **하이라이트 색(accent-1)** 강조
- 상단 필터 칩: `영감 주는 사람` / `정반대 성향` / 16유형 코드별

### 4-2. 프로필 상세 — 오버레이 비교

- **내 그래프(실선) + 상대 그래프(점선)** 오버레이: 핵심 "아하 모먼트"
- 차이 설명 카피: `"협업 축에서 정반대예요"` (이유 항상 노출)

### 4-3. 진단 미완 유저가 프로필 상세 진입 시 (폴백)

**진입 경로**: 포트폴리오 피드 → 작품 상세 → 업로드 유저 프로필 등 발견 탭 우회 경로

**처리 방식**: 오버레이 영역 제거 → **상대방 그래프 단독 표시**

```
┌─────────────────────────┐
│  [상대방 5각형 그래프]   │
│                         │
│  "이 사람의 성향이에요"  │
│                         │
│  ┌─────────────────┐   │
│  │ 나의 성향 확인  │   │  ← CTA 버튼
│  │   해보기 →      │   │
│  └─────────────────┘   │
└─────────────────────────┘
```

- 오버레이 UI는 완전 제거 (흐릿 처리 아님)
- CTA 탭 시 → 프로필 탭의 성향 진단 시작 화면으로 이동

## 5. 발견 진입점 (확정)

### 진입점 ①: 검사 직후 결과 화면

- 진단 완료 → 결과(유형 코드 + 5각형) 표시
- **자동으로** "나와 반대인 사람 1명 / 닮은 사람 1명" 오버레이 미리보기
- "더 보기 →" → 발견 화면(`/people`) 전체 피드

### 진입점 ②: 프로필의 5각형 꼭짓점 클릭

- 내 프로필 5각형은 인터랙티브
- 특정 축(꼭짓점) 클릭 → `"이 축에서 나와 반대인 사람 보기"` 필터 적용된 발견 피드

### 진입점 ③: 포트폴리오 피드 경유 직접 진입

- 경로: 포트폴리오 피드 → 작품 상세 → 업로드 유저 프로필
- 발견 화면 게이트를 우회하는 경로 — 진단 미완 유저도 도달 가능
- 진단 여부에 따른 프로필 상세 처리: → [4-3. 폴백 규칙](#4-3-진단-미완-유저가-프로필-상세-진입-시-폴백) 참조

### 참고: 하단 탭바에 발견 탭 없음 (확정)

`/people` 라우트는 존재하지만 TabBar에 탭으로 노출하지 않는다.

**이유**: 상시 브라우징 탭은 데이팅 앱의 전형적 UI 구조로, "연애 매칭 아님" 원칙과 가장 직접적으로 충돌한다. 발견은 자연스러운 맥락(진단 직후, 프로필 탐색 중)에서만 진입 가능하게 제한한다.

**트레이드오프**: 탭이 없으므로 현재 반복 가능한 유일한 경로는 진입점 ②(내 프로필 5각형 꼭짓점 클릭)뿐이다. 진입점 ①(검사 직후)은 검사를 재실시하지 않는 한 재진입 불가. 진입점 ③은 구현 범위 밖. 이 제약을 수용하는 것이 이번 결정의 의도적 선택이다.

## 6. 추천 로직 (확정)

### 6-1. 거리 기반 정렬

| 진입점 | 거리 계산 |
|---|---|
| 검사 직후 | 5축 전체 유클리드 거리 합산 |
| 5각형 축 클릭 | 해당 축 1개만의 차이값으로 정렬 |

- 거리 최대 ≈ 전 축 반전 = 완전 반대 유형 자동 산출
- 거리 최소 ≈ 닮은 유형

### 6-2. 후보 필터

1. 포트폴리오 작품 1개 이상 업로드 (작업 실체 확인)
2. 최근 활동 있음 (기준: 별도 결정 필요)
3. 발견 노출 opt-in 상태

### 6-3. 랜덤화

- 상위 N명 중 **약한 랜덤화** (매번 동일인 반복 방지)
- N값: 구현 시 결정 (10~20 권장)

### 6-4. 이유 설명 카피 (블랙박스 방지)

모든 추천 카드에 이유 문구 필수 노출:
- `"협업 축에서 정반대예요"`
- `"작업 방식이 가장 닮았어요"`

## 8. 컨택 → 팀 결성 플로우 (확정)

### MVP — 관심 표현 → 수락 → DM 개방 (B안)

1. 프로필 상세에서 **"관심 있어요"** 버튼 탭
2. 상대방에게 알림 — 수락/무시 선택
3. 상대방이 수락하면 **양방향 DM 채널 개방**

**구현 비용**: 대화 테이블에 `is_accepted: boolean` 필드 하나 추가. 수락 전 메시지 전송 시도 시 → 거부 처리.  
**선택 이유**: 발견 노출 opt-out·컨택 수신 제한이 FULL-LEGAL-1으로 미뤄진 상태에서 즉시 오픈 DM을 유지하면 사전 동의 장치 없이 사후 차단/신고에만 의존하는 구조가 됨. 관심 표현→수락은 최소 비용으로 사전 동의를 확보하는 구조.

### 미결 구현 질문

- 채팅 인프라 방식: WebSocket vs. 폴링 (구현 단계 결정)
- 채팅방 UI: 기존 채팅 기능 유무 확인 필요
- 메시지 스레드 관리: 1:1 채팅방 vs. 요청 인박스

## 12. 재진단 (Retest) — 확정 2026-09-05

이미 진단을 완료한 유저가 다시 진단받는 경로. 팀 내부 People 탭 데모/테스트에서 반복 진단이 필요해 추가.

### 12-1. 조사 결과: 백엔드는 이미 지원하고 있었음

`PersonalityAssessmentView`(`apps/accounts/views/personality.py`)가 처음부터 upsert로 구현돼 있음:

```python
personality, created = PersonalityProfile.objects.update_or_create(
    user=profile,
    defaults={'axis_1': a1, ..., 'type_code': type_code},
)
evict_user_profile_detail(profile.user.id)      # 프로필 상세 캐시 무효화
return Response(..., status=201 if created else 200)   # 재진단은 200
```

이력 테이블이 없어 **최신 결과 하나만 유지**되며, 이는 기존 모델 설계 그대로다. 따라서 "override" 요구사항은 **백엔드 변경 없이 이미 충족**된다.

막혀 있던 것은 UI 진입점뿐이었다 — `UserProfilePage`가 `personality`가 **없을 때만** `성향 진단 받기` CTA를 띄우고, **있으면** 오각형 차트만 보여줘서 다시 들어갈 문이 없었다. (`/assessment` URL 직접 입력은 그 전에도 동작했다.)

### 12-2. 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 버튼 위치 | 내 프로필, 오각형 차트 + `{type_code} 유형` 문구 **아래** | 바로 위 형제 분기(`personality` 없음)의 `성향 진단 받기` CTA와 같은 자리 → 두 상태가 대칭. 유저가 자기 성향을 확인하러 오는 곳이라 발견성도 좋음 |
| 확인 모달 | **없음**, 클릭 즉시 `/assessment` | 제출 전에는 아무것도 안 바뀜(`update_or_create`가 제출 시점에만 실행). 중간 이탈해도 이전 결과가 남으므로 보호할 대상이 없고, 반복 데모에 마찰만 됨 |
| 시작 지점 | **항상 1번 문항부터** | "다시 진단받기"라는 문구와 동작 일치. 데모에서 매번 같은 상태로 시작되어 예측 가능 |
| 버튼 스타일 | 기존 CTA 값 그대로 재사용 | `padding:10px 20px` · `--radius-pill` · `--color-surface` · `1px solid --color-border` · `13px/600` · `minHeight:36`. 새 값 미생성 |

### 12-3. 데이터 흐름 (변경 없음)

```
[다시 진단받기] → /assessment (1번 문항)
   → 20문항 완료 → POST /personality/assessment/
       → PersonalityProfile.update_or_create(...)   덮어쓰기
       → evict_user_profile_detail(user.id)         캐시 무효화
       → 200

프로필  GET /users/<id>/  → 캐시가 비워져 새 축/type_code 반환
People  GET /people/      → 캐시 없음, 매 요청 DB 직조회 → 새 벡터로 정렬·그래프 갱신
```

### 12-4. 엣지 케이스

- **중간 이탈** — 제출 전이므로 이전 결과 유지. 확인 모달이 불필요한 이유
- **제출 실패** — 기존 재시도 UI 동작, 이전 결과 유지
- **`personality` 없는 유저** — 이 분기에 진입하지 않으므로 영향 없음

### 12-5. 후속 조치 (미해결)
