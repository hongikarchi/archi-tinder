# 사람 관계 모델: 관심 요청 → 팔로우

**작성** 2026-11-21 · **작업** SNS-FOLLOW-1 · **상태** 사용자 결정 확정 · 구현 완료, 기능 플래그 `FOLLOW_ENABLED` OFF · **대체** `2026-10-02-contact-messaging-design.md`의 D3·D10·D11·D13

## 1. 문제

"관심 있어요"를 누르면 인사말 시트가 열리고 바로 요청이 나갔다. 관계를 맺는 행위와 말을 거는
행위가 하나로 묶여, 가볍게 관계만 맺을 방법이 없었다. 수락/무시와 30일 쿨다운은 그 결합을
지탱하려고 생긴 장치였고, 무시 사실이 30일 뒤 드러나는 누수(#409)도 여기서 나왔다.

## 2. 결정

### `discovery_opt_in`의 의미 확장

이전: 발견 피드 노출 + 성향 숨김. **이후: 발견 피드 노출 + 성향 숨김 + 신규 팔로우 수신 차단.**
설정 화면 안내문(`settings.discoveryHint`)에 "끄면 다른 사람이 나를 팔로우할 수 없습니다"를 넣어
토글이 실제로 하는 일과 문구를 맞춘다. 끄더라도 기존 팔로워는 유지된다 (F7).

### `is_guest` 판정 위치

팔로우/메시지 코드에서 게스트 판정은 `apps/social/services.py`의 단일 함수(`is_guest_account`)
안에서만 한다. 게스트 경로 제거(#443)가 실행되면 그 함수 하나만 고친다.

## 3. 데이터 전환

`messaging` 마이그레이션이 기존 `ContactRequest`를 변환한다. 운영 DB의 건수는 아직 확인하지
못했으므로, 건수와 무관하게 안전하고 멱등하게 동작한다 (상태별 건수를 먼저 출력하고, 대상이 0건이면 아무것도 하지 않는다).

| 기존 상태 | 변환 |
|---|---|
| accepted | 양방향 `UserFollow` (서로 팔로우) |
| pending | 보낸 사람 → 받은 사람 단방향 `UserFollow`. 관심 보내기는 일방적 호감 표시라 팔로우와 의미가 같고, 받은 쪽에서는 "맞팔로우" 상태로 이어진다 |
| ignored | 변환하지 않음. 명시적으로 거절된 관계이고, 팔로워 제거 기능이 없어 팔로우로 만들면 되돌릴 수단이 차단뿐이다 |

차단 관계인 쌍은 건너뛴다. pending은 받은 사람이 게스트이거나 opt_out이면 건너뛴다.

`ContactRequest` 모델은 코드에서 제거하지만 **테이블은 남긴다** (Django 상태에서만 삭제,
`SeparateDatabaseAndState`). 공용 개발 DB와 운영 DB에서 데이터 삭제를 하지 않기 위해서다.
Django가 더 이상 이 테이블을 cascade하지 않으므로, 계정 삭제가 막히지 않도록 테이블의 FK
제약만 제거한다 (행은 보존). 테이블 삭제는 후속 이슈로 추적한다.

## 4. 폐기된 것

인사말, 받은 요청 목록, 수락/무시, 30일 쿨다운, 서로 관심 즉시 연결, "연결됐어요" 시스템 메시지
발행, 탭바 점의 "받은 요청 수" 합산 (이제 안 읽은 메시지만). 이미 저장된 "연결됐어요" 시스템
메시지는 화면에서 표시하지 않는다.
