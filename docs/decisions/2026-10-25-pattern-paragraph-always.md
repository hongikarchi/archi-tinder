# 패턴 분석 문단 항상 표시

**작성** 2026-10-25 · **브랜치** `feature/claude-pattern-always` · **상태** 사용자 결정 확정 · 구현 중

## 1. 문제

페르소나 리포트의 「패턴 분석 결과」 문단(`final_report.pattern_paragraph`)이 리포트마다 나왔다 안 나왔다 한다.

- 문단은 통계 사실(`compute_taste_facts`)이 하나 이상 있을 때만 쓰였다. 사실 조건: 특징이 보인 건물 ≥ 3, 좋아요 ≥ 2, 좋아요 비율 ≥ 1.5배(라플라스 보정).
- 10~15번 스와이프, 특히 싫어요가 적은 세션은 비교 대상이 없어 사실이 0개가 되기 쉽고, 그러면 서버가 문단을 `''`로 비웠다(`generation.py`의 `if not facts`).
- 화면은 제목만 남거나(결과 카드) 섹션이 사라져(리포트 페이지) 오류처럼 보였다.

## 2. 결정 (사용자, 2026-10-25)

> "진짜로 객관적으로 맞는 분석 문장인지 보다는 그럴듯해보이는 분석 문장이 항상 나오는게 더 중요하다."

- 문단은 **항상** 나온다. 엄격한 통계 유의성보다 그럴듯함을 우선한다.
- **지키는 선:** 문장에 들어가는 **숫자는 반드시 실제 데이터에서 계산한 값**만 쓴다. 숫자 없는 해석 문장은 자유롭게 쓴다. (숫자를 지어내면 사용자가 자기 기록과 대조할 때 바로 틀린 게 드러나 신뢰가 깨진다.)
- Product Constitution 원칙 4(정직한 매칭 > 참여 지표)와의 관계: 이 결정은 **추천·매칭 품질**이 아니라 **리포트 문구 노출**에 관한 것이다. 매칭 알고리즘은 바꾸지 않는다. 숫자 사실은 여전히 실제 값이라 정직성의 핵심은 유지된다.

## 3. 설계 — 단계별 근거

| 단계 | 조건 | 문장 | `pattern_source` |
|---|---|---|---|
| 1 | 기존 엄격 사실 있음 | 기존 템플릿 ("보여드린 건물 중 … 약 N배 자주 고르셨어요") | `facts` |
| 2 | 1 없음 → 완화 기준(보인 ≥ 2, 좋아요 ≥ 2, 비율 ≥ 1.2) | 같은 템플릿 | `relaxed` |
| 3 | 2 없음 → 좋아요 구성 | "좋아요한 N곳 중 M곳이 X 건물이었어요" (실제 개수) | `composition` |
| 4 | 3 없음 | LLM 해석 문장, 숫자·비교 주장 금지 ("고르신 건물들을 보면 …") | `interpretive` |
| — | LLM이 문단을 비워 보냄 | 서버가 1~3 사실로 템플릿 문장을 직접 조립 → 없으면 상위 좋아요 태그 문장 → 없으면 일반 문장 | `fallback` |

- 완화 기준 값은 `backend/config/settings.py` RECOMMENDATION의 `report_fact_relaxed_*` 키(값의 단일 출처).
- 싫어요 사실의 `building_ids` 비노출 규칙, `is_publishable` 게이트는 그대로.
- 프론트: 언어별 빈 문자열은 없는 값으로 취급(다른 언어/최상위로 대체). 예전에 저장된 빈 문단 리포트는 두 화면 모두 「더 둘러보시면 취향 패턴을 분석해 드릴게요」를 흐리게 표시.

## 4. 범위 밖

- 매칭·추천 알고리즘 변경 없음.
- 기존 저장 리포트 일괄 재생성 없음(다음 재생성 때 새 규칙 적용).
