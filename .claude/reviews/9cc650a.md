## Findings (Part A)

### 1. [CRITICAL] BuildingDetailPage bookmark POSTs `rank: null` → backend always 400
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:231` (call site) + `frontend/src/api/projects.js:96-103` (no null strip) + `backend/apps/recommendation/views/swipe.py:204-208` (validator)
- **Axis:** 2. Correctness & logic depth
- **Issue:** `handleToggleBookmark` calls `bookmarkBuilding(fromProjectId, buildingId, ..., null, fromSessionId)` with literal `null` for rank. `bookmarkBuilding` spreads `rank` unconditionally into the JSON body, so `JSON.stringify` emits `"rank": null`. `ProjectBookmarkView.post` (line 204) checks `if not isinstance(rank, int) or rank < 1 or rank > 100` and returns 400 (`{"detail": "rank must be integer in [1, 100]"}`). The view does not use a serializer — there is no other validation path that could rescue this. Every click on the new BuildingDetailPage star button results in:
  1. Optimistic UI flip ☆ → ★.
  2. Backend 400 (logged in console as a network error).
  3. Bare `catch {}` (line 232-234) reverts UI back to ☆ silently.
  4. User sees the star animate-then-disappear and assumes "it didn't take" — no error toast.
- **Why it matters:** The new feature does not function at all in production. Worse, the silent revert hides the failure from telemetry that watches console error counts; only network logs would catch the 400 storm. This is also the spec's primary success metric (`saved_ids`) being wired up — shipping it broken is a direct regression of the metric pipeline that exists for it.
- **Suggested fix:** Pass a real `rank` end-to-end. Two paths:
  - **From ResultsPage entry:** include `rank` in the location state alongside `fromProjectId` / `fromSessionId`, and use it on BuildingDetailPage. (Easy — ResultsPage already iterates with `index + 1`.)
  - **From non-ranked entries (BoardDetailPage, ProjectCard):** the bookmark concept doesn't have a meaningful rank. Either (a) relax the backend validator to accept missing/null `rank` for non-result-page bookmarks (and key the rank_zone / rank_corpus telemetry off `rank is not None`), or (b) hide the bookmark control entirely on those entries (likely better — see MAJOR #2 — those contexts also have the ownership problem).
  - Pair with at least a backend-test asserting the success and 400 paths so future drift is caught.

### 2. [MAJOR] BuildingDetailPage bookmark state never syncs from `Project.saved_ids`
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:175-176, 178-207`
- **Axis:** 2. Correctness & logic depth
- **Issue:** `isBookmarked` initialises to `useState(false)` and there is no effect that reads the project's `saved_ids` to reflect the true persisted state. Whether the user opens a building they have never bookmarked or one they bookmarked yesterday, the star always shows ☆ on first paint. Clicking then optimistically flips to ★ and (once the CRITICAL is fixed) sends `action: 'save'`. If the building was already saved, this is silently a no-op on the backend (set semantics, line 218-220) and the UI then reflects ★ correctly only by coincidence. Navigating away and back loses the local state again.
- **Why it matters:** Core trust in the bookmark UI is broken. The user cannot rely on the star icon to tell them whether a building is in their collection. Combined with the CRITICAL above, fixing only the rank problem leaves the user clicking ★ on every visit thinking they're "saving again" each time.
- **Suggested fix:** When `building` and `fromProjectId` are both available, look up whether `buildingId` is in the project's `saved_ids` and seed `isBookmarked` accordingly. Either (a) thread `savedIds` down via location state from ResultsPage / parent that already knows it, (b) extend the route-level `projects` array (already in `App.jsx`) to be readable here via context, or (c) add a lightweight `GET /api/v1/projects/<id>/` lookup on mount. Option (a) is cheapest if the entry surface is small; (b) scales as more entry points appear.

### 3. [MAJOR] Bookmark UI rendered without ownership check — silent 404 from non-owner contexts
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:260` (`bookmarkEnabled={!!fromProjectId}`) + `frontend/src/pages/BoardDetailPage.jsx:673` (passes `fromProjectId={boardId}`) + `frontend/src/components/profile/ProjectCard.jsx:23` (passes `fromProjectId: project.project_id`)
- **Axis:** 2. Correctness & logic depth (UX) / 4. Security in depth (IDOR-shape signal, though not exploitable)
- **Issue:** `bookmarkEnabled` is set whenever `fromProjectId` is truthy — but `fromProjectId` is forwarded indiscriminately:
  - From **`BoardDetailPage`**, it equals `boardId` (a UUID validated only as well-formed, not as owned). Public boards belong to other users.
  - From **`ProjectCard`** (firm profile), it equals `project.project_id` of the firm's project — never the viewer's.
  - From **`ResultsPage`**, it equals the user's own project — correct.
  Backend `ProjectBookmarkView` filters `Project.objects.get(project_id=project_id, user=profile)` (line 187) and returns 404 on miss. So a viewer on someone else's public board who clicks the building's bookmark star sees the same silent revert pattern as the CRITICAL.
- **Why it matters:** The bookmark control appears available in three contexts but only functions in one. The two non-functional contexts will never error visibly — same silent-revert cycle. This will read as "the bookmark feature is flaky / ours doesn't always save" in user feedback once the rank CRITICAL is fixed.
- **Suggested fix:** Tighten the entry contract. `BoardDetailPage` already loads `board.user.user_id` (used for the owner-row). Compare to the logged-in user; if they don't match, do not pass `fromProjectId` — the bookmark icon disappears. Same for `ProjectCard`: the firm-profile project is never the viewer's, so do not pass `fromProjectId` from there at all (the click navigates to building detail without bookmark UI). Alternatively (out of scope for this branch but discuss): treat "bookmark from non-owner context" as "save to my default project", which would require a much bigger UX decision.

### 4. [MINOR] `engine.py` bandwidth — full text columns added to 5 SELECTs that don't need them
- **File:** `backend/apps/recommendation/engine.py:219, 275, 325, 359, 384, 1509`
- **Axis:** 3. Performance & optimization
- **Issue:** `visual_description` (rich text) + `description` are now selected by `get_diverse_random`, `get_top_k_results`, `search_by_filters`, `get_top_k_mmr` (50-row Top-K result), and `get_buildings_by_ids` — but only `get_buildings_by_ids` actually surfaces the rich text to the BuildingDetailPage. The Top-K MMR path returns up to 50 rows; per-row visual_description appears to be 200-2000 chars, so rough order ~50 KB extra payload per `/swipes/` round when it returns Top-K. Not an immediate problem on a fast network, but the page is also receiving the same fields it's never going to read.
- **Why it matters:** Cumulative bandwidth + JSON parse cost on every swipe response, with zero consumer. The same data is one extra `_row_to_card` allocation per row (small but not free).
- **Suggested fix:** Either (a) restrict `visual_description` / `description` to `get_buildings_by_ids` only and have BuildingDetailPage rely on its own batch fetch (the simplest split — already happens via `getBuildings([buildingId])`), or (b) keep the columns selected but trim them out of `_row_to_card.metadata` for Top-K paths via a flag. Option (a) keeps the surface area smallest. Optional: defer to a follow-up MINOR commit.

### 5. [MINOR] BuildingDetailPage useEffect race when `buildingId` changes mid-bookmark
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:178-207, 225-237`
- **Axis:** 2. Correctness & logic depth
- **Issue:** When the user navigates from one building to another (back/forward, or deep-link change) while a bookmark request is in flight, the new building's render inherits `isBookmarked` and `bookmarkPending` from the previous building. The pending request's `setBookmarkPending(false)` will fire after the new building has loaded, briefly leaving the new star in a stale state. The fetch effect resets `building` / `loading` / `error`, but not the bookmark state.
- **Why it matters:** Edge-case visual glitch; not a correctness violation by itself but contributes to the "bookmark feels janky" gestalt.
- **Suggested fix:** Reset `isBookmarked` and `bookmarkPending` inside the buildingId-change effect (or move bookmark state below the loading guard).

### 6. [MINOR] ResultsPage IntersectionObserver can rapid-fire batch loads
- **File:** `frontend/src/pages/ResultsPage.jsx:163-173`
- **Axis:** 3. Performance & optimization / 2. Correctness
- **Issue:** The effect re-creates the observer on every `loadedRank` change. If the sentinel is still in the viewport when the new observer attaches, IntersectionObserver fires synchronously in the next microtask, increment again, attach a new observer — each iteration is one frame. On small `cappedTotal` (e.g. 12-20 cards) the user sees 10 → 20 → 30 → 40 → 50 expand effectively at once, defeating the "lazy" intent.
- **Why it matters:** Visual jank on small result sets; can also cause DOM churn during a scroll.
- **Suggested fix:** Either (a) gate the observer's `setLoadedRank` behind a per-effect `triggered` flag so it fires once per attach, or (b) keep one observer instance across renders (mount once, observe the same sentinel) and gate inside the callback.

### 7. [MINOR] No tests added for new bookmark flow or lazy-load
- **File:** `backend/apps/recommendation/tests/`, `frontend/src/`
- **Axis:** 6. Test coverage
- **Issue:** The new BuildingDetailPage bookmark path (and the `rank: null` contract mismatch in particular) would have been caught by even a minimal integration test that asserts `POST /projects/<id>/bookmark/` from the BuildingDetailPage code path with the rank value the frontend actually sends. None exists. Same gap for the IntersectionObserver pagination.
- **Why it matters:** Cross-cutting feature work without contract tests is exactly how the CRITICAL #1 slipped through.
- **Suggested fix:** Add at least a `pytest` case in `backend/tests/` that posts `{card_id: "...", action: "save", rank: null}` and asserts the current 400 (or, post-fix, the new shape). Frontend testing would also help but is consistent with the project's existing posture (low coverage).

## Security Analysis

- `ProjectBookmarkView` correctly enforces ownership via `Project.objects.get(project_id=project_id, user=profile)` (line 187). Attackers cannot bookmark to other users' projects — they get 404. The frontend MAJOR #3 is a UX bug, not a privilege escalation.
- `building.source_url` is rendered as `<a target="_blank" rel="noopener noreferrer">`. `rel` is correct (blocks `window.opener` attacks). The href value comes from the database, not user input. A `javascript:` scheme would still be fired by the anchor — defensive scheme validation (allowlist `https?:`) would be belt-and-suspenders, but the data source is curated. Not a finding, mentioned for completeness.
- `BUILDING_ID_RE = /^[A-Za-z0-9_-]{1,32}$/` (BuildingDetailPage) and `UUID_RE` (BoardDetailPage) correctly validate URL params before fetching. ✓
- No raw SQL injection risk in the engine.py changes — column lists are static identifiers, not user data.
