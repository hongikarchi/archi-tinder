### 2. [MINOR] `useResults.toggleBookmark` discards the server-authoritative saved_ids response

- **File:** `frontend/src/hooks/useResults.js:81-91`
- **Axis:** 2 (Correctness & logic depth)
- **Issue:** `bookmarkBuilding(...)` returns `{saved_ids, count}` per `ProjectBookmarkView` (`backend/apps/recommendation/views/swipe.py:292-294`). The hook awaits the call but never reads the response body — it relies entirely on the optimistic update applied at line 72-79. If a different tab / device concurrently modified `saved_ids` between this user's render and click, local state diverges from backend truth.
- **Why it matters:** Today the only writer of `saved_ids` for a given user is the user themselves, so divergence is rare. As Phase 13+ (BOARD3 reactions, Phase 16 social) layers more concurrent state mutations, the server-authoritative override pattern (already used in `BoardDetailPage` reaction toggle's `setReaction({reaction_count, reacted})` from POST 201) becomes the right pattern for bookmarks too.
- **Suggested fix:** After `await bookmarkBuilding(...)` resolves with `resp`, reconcile via `setProjects(prev => prev.map(p => p.id === project.id ? { ...p, savedIds: resp.saved_ids } : p))`. Mirrors BOARD3 cycle 0 contract-correctness pattern.

### 4. [MINOR] Duplicate `getResult` fetch on auto-navigate (App.jsx → ResultsPage)

- **File:** `frontend/src/App.jsx:393-405` + `frontend/src/hooks/useResults.js:38`
- **Axis:** 3 (Performance & optimization)
- **Issue:** When swipe session completes (`is_analysis_completed`), App.jsx calls `api.getResult({...})` to populate `predictedLikes` in state (line 393), then `navigate('/result/${project.sessionId}')` in finally (line 405). ResultsPage mounts → `useResults` effect 2 unconditionally calls `getResult` AGAIN (line 38). Two round-trips for the same data; the second overwrites the first transparently. Empirically `getResult` ran 2910ms in this review's browser test — a 3-second redundant fetch in the most user-perceptible moment of the flow (post-swipe transition).
- **Why it matters:** Wasted ~3s round-trip when the data is already in `project.predictedLikes` after App.jsx's pre-fetch. Not a bug, but a perf opportunity that compounds with the result-page rerank pipeline cost.
- **Suggested fix:** Pass a `state.skipFetch` flag via `navigate('/result/...', { state: { resultData } })` and have `useResults` consume it on first mount. Or simpler: use `predictedLikes` as the source of truth and only fall back to `getResult` if it's empty. Out-of-scope for Phase 1; Phase 2 candidate.

### 7. [MINOR] Layout viewport split is tight on small mobiles (< 720px height)

- **File:** `frontend/src/pages/ResultsPage.jsx:155-220`
- **Axis:** 1 (Architecture alignment) — spec § 8 first-card-visibility constraint
- **Issue:** Persona section: `minHeight: '34vh', maxHeight: '40vh'`. Carousel section: `minHeight: '60vh'` (cards inside have `height: 'min(58vh, 520px)'`). Page wrapper height `calc(100vh - 64px - env(safe-area-inset-bottom, 0px))` ≈ ~95vh effective. On a 360×720px mobile (= 656px effective height after 64px tab bar), 34% = 223px persona + ~30px carousel header + 58vh card = ~641px content vs 656px viewport — leaves ~15px slack. Tightens further on devices with safe-area-inset-bottom > 0px (iPhone notch class). Spec § 8 line 346: "Initial viewport에서 Top-K 첫 카드가 최소 1개는 보여야 함 (scroll 안 내리면 bookmark 행동이 일어나지 않음 → metric 오염 방지)." Plan §1 line 122-125 (open question #5) flagged this — Phase 1 acceptable but worth a small-mobile pass eventually.
- **Why it matters:** The user types `% 34vh + 60vh = 94vh` math works on most viewports but leaves no margin on small phones for the carousel-header text + card. If the bookmark is consistently slightly off-screen on a popular mobile size, primary-metric (`top-10 bookmark rate`) would be artificially deflated — exactly the metric-pollution the spec's first-card-visibility rule is designed to prevent.
- **Suggested fix:** Either tighten persona section maxHeight to `35vh` (was `40vh`) on the first viewport, OR add a `min-height: 200px` on the first card with explicit constraint, OR request a designer pass for small-mobile audit. Designer territory; flag as `// TODO(designer): small-mobile first-card visibility audit` if not deferred.

## Security Analysis

- **No new auth surface.** `useResults` reads no tokens directly; relies on `bookmarkBuilding` → `callApi` → `core.js` shared interceptor (Authorization Bearer + 401 refresh path).
- **UUID guard on path param** (`useResults.js:13`): `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`. Mirrors FirmProfilePage `/^[A-Za-z0-9_-]{1,64}$/` and BoardDetailPage UUID-guard defense-in-depth pattern. Correct case-insensitive flag.
- **Authorization: backend-enforced.** `ProjectBookmarkView.post` (`swipe.py:181-189`) does `Project.objects.get(project_id=project_id, user=profile)` → 404 on cross-user access. Same pattern for `SessionResultView` (`sessions.py:336-339`). Frontend's project-find by sessionId is purely UX convenience; the security gate is server-side.
- **Input validation: backend-enforced.** `card_id` length ≤ 20, `action ∈ {save, unsave}`, `rank ∈ [1, 100]` (`swipe.py:196-208`). Frontend doesn't pre-validate, but invalid inputs would 400 — handled by `bookmarkBuilding`'s catch and surfaces as rollback.
- **No `dangerouslySetInnerHTML`, no token-in-URL, no `console.log` of PII.** Verified.
- **Same-origin fetches only** (`callApi` strips host prefix; backend at `:8001` is dev-only same-machine).
- **No new permission_classes / new model — no IDOR surface.**
