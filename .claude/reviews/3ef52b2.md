## Findings (Part A)

### 1. [MINOR] Dead-code branch in `validate_display_name`
- **File:** `backend/apps/accounts/serializers.py:88-91`
- **Axis:** 5 (Code quality)
- **Issue:** `display_name` is declared as `serializers.CharField(trim_whitespace=False, allow_blank=True, required=False, max_length=30, ...)`. Then `validate_display_name` does:
  ```python
  if len(stripped) > 30:
      raise serializers.ValidationError('display_name must be 30 characters or fewer.')
  ```
  This branch is **unreachable**. CharField's `max_length=30` runs *before* `validate_<field>`, and stripping can only reduce length: `len(stripped) > 30` requires `len(value) > 30`, which `max_length=30` already rejects with DRF's default error `"Ensure this field has no more than 30 characters."`. Empirically verified just now:
  ```
  PATCH {"display_name": "a" * 31}
  → 400 {"display_name": ["Ensure this field has no more than 30 characters."]}
  ```
  The custom message never fires.
- **Why it matters:** Cosmetic now (behavior is correct: 30-char limit holds). Future-maintainer hazard: someone reading the validator would assume the custom error is what users see; might extend the dead branch with a follow-up check that also never runs.
- **Suggested fix (one of):**
  - **(a) Drop the branch** — `if len(stripped) == 0: raise ...; return stripped`. CharField `max_length` handles the upper bound. Net -3 lines.
  - **(b) Drop `max_length=30` from CharField** and keep the custom message — makes the custom validator the single source of truth (consistent error wording with the whitespace-only message).
  - **(c) Add a comment** acknowledging the redundancy: `# Belt: max_length=30 fires first; this is documentation-only.`
  Either (a) or (b) is preferable to (c). (a) is the simplest.

## Observations (sub-MINOR, not flagged as findings)

1. **`useProjectReactors` has no in-flight cancellation** when `projectId` changes mid-fetch. The `useEffect` calls `reset()` which clears state, but a pending `getProjectReactors` for the previous projectId can land its response into the new state shape. Typical use case (open one project's reactor list) wouldn't trigger this; project-hopping while a fetch is in flight would. AbortController would close it cleanly.

2. **`team-back.md` and `team-front.md` live alongside the standard Claude Code agent registry** at `.claude/agents/*.md`. They're authored for **Codex CLI** sessions running in cmux workspaces (`team-back.md` line 13: "Your tab runs `codex` (OpenAI Codex CLI) by default"). But the standard Claude Code harness loads every `.md` under `.claude/agents/` as a selectable `subagent_type`. If a user (or Claude itself) types `subagent_type=team-back` from the main session, a Claude session would spawn that thinks it's Codex — confusion, not security risk. Mitigation options: subdirectory (`.claude/agents/codex/`), naming prefix (`codex-team-back.md`), or a header note like "Do not invoke from Claude's Agent tool."

3. **Bio whitespace-only-as-clear behavior is not tested**. Commit `27fee9b` body says "Whitespace-only is treated as 'clear the bio' rather than rejected" but the test diff shows only `test_bio_too_long_rejected`. A `test_bio_whitespace_only_clears_field` (mirroring the existing `test_patch_self_mbti_whitespace_only_clears_field` at line 229) would close this gap.

4. **`b272f37` refactor crosses the design-pipeline-territory line** *technically* — it moves JSX with inline styles into new files. But the commit explicitly says "Behavior unchanged. Inline styles preserved verbatim. TODO markers preserved." This is structural only; the styles themselves are unchanged. Per CLAUDE.md `## Rules` ("UI vs Data split inside the same `.jsx` file is enforced **per-line, not per-file**"), the refactor is borderline. Two interpretations:
   - **Strict reading**: moving JSX between files is design territory because component boundaries affect future style maintenance.
   - **Pragmatic reading**: a structural refactor that preserves style content verbatim is data-layer cleanup (reducing merge-conflict surface for the SNS dev per BRANCHING.md role B) and the styles themselves are untouched.
   I read this as pragmatic-and-justified given the commit's explicit BRANCHING-rationale + "preserved verbatim" claim, and don't flag as a finding. Worth noting if the design pipeline subsequently disputes it.

5. **`cmux_setup.sh` 8-second sleep** between `cmux new-workspace` and the init-prompt send. Empirically tuned for codex/claude startup splash on the user's machine; could be flaky on slow disks. Acceptable for a one-off setup script (idempotent, won't run again unless workspaces are torn down).

6. **`dispatch.sh` strips newlines via `tr '\n' ' '`** (line 67) because `cmux send` types the message literally and a newline would submit prematurely. Documented in line 65-66. Side effect: any newline in the dispatched message becomes a space, including ones the user genuinely intended (e.g., a multi-step task description). Cosmetic — the receiving agent reads the same intent regardless.

7. **`b272f37` officeId guard regex** `/^[A-Za-z0-9_-]{1,64}$/` (FirmProfilePage line 87) accepts up to 64 chars. The OFF001-style IDs from the spec are typically 6-10 chars. The 64-char ceiling is generous but not unreasonable as a defense-in-depth allowlist. Could be tightened to `{1,32}` if there's confidence about the ID format from PROF1.
