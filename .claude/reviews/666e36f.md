## Findings (Part A)

### 1. [MINOR] Non-transactional bulk-bookmark in SurpriseBoardModal can leave an orphan board
- **File:** frontend/src/components/SurpriseBoardModal.jsx:54-69
- **Axis:** 2 (Correctness)
- **Issue:** `handleSaveBoard` POSTs `/projects/` to create the board, then runs `for i…cards` calling `bookmarkBuilding` sequentially. If any bookmark call rejects (network blip, 5xx, partial 4xx), the catch sets `phase='error'` and the board persists with 0–N saved buildings. The `handleRetry` path only re-fetches the surprise pool — there is no compensating delete and no retry of the partially-saved board, so the next "Save this board" tap creates a *second* board with the same name.
- **Why it matters:** Real-world bookmark loop is 10 sequential RTTs to a JWT-auth Neon route — failure probability is non-trivial. User ends up with phantom boards in `/profile`, no way to recover from inside the modal.
- **Suggested fix:** Either (a) wrap the loop in a single bulk-bookmark POST endpoint (`POST /projects/{id}/bookmarks/bulk/` with idempotency on building_id), or (b) on bookmark-loop failure issue `DELETE /projects/{id}/` to roll back the orphan and surface the failure as a clean retry. Out of scope for S7 if a follow-up story exists; otherwise S8 candidate.

### 2. [MINOR] Exclusion-set construction duplicated across DiscoveryFeedView + BoardSurpriseView
- **File:** backend/apps/recommendation/views/discovery.py:46-66 and 115-135
- **Axis:** 5 (Code quality) / 7 (Cross-commit drift)
- **Issue:** The two views contain identical 21-line blocks that fetch `Project.objects.filter(user=profile).values('liked_ids', 'disliked_ids', 'saved_ids')`, dedupe across types, and return both an ordered list and a set. Nothing diverges between callers.
- **Why it matters:** Any future fix (e.g. when `disliked_ids` shape evolves to `[{id, intensity}]`, or when a 4th list joins) must be applied twice. Drift risk grows when later phases extend exclusion semantics.
- **Suggested fix:** Extract `_collect_user_exclusions(profile) -> tuple[list[str], set[str]]` into `views/_shared.py` (precedent: `_liked_id_only`, `_get_profile`, `_progress` already live there). Both views drop to a one-liner.

### 3. [MINOR] `taste_ranked_page` computes pgvector distance twice per row
- **File:** backend/apps/recommendation/engine.py:1830-1845
- **Axis:** 3 (Performance)
- **Issue:** The CTE selects `embedding <=> %s::vector AS score` and the same expression is repeated in `ORDER BY embedding <=> %s::vector ASC`. Two distance computations per candidate row. PostgreSQL's planner often deduplicates identical projections, but the two literals are bound as separate parameters so they look distinct to the planner, which may not collapse them.
- **Why it matters:** Discovery feed is the new home tab — every page-load and infinite-scroll fetch hits this query. With ~25k candidate rows in `architecture_vectors`, even a 30% computed-twice penalty matters.
- **Suggested fix:** Reuse the alias: `ORDER BY score ASC` inside the CTE, drop the second `%s::vector` placeholder, drop the second `_vec_to_pg(v_taste)` from the params list. EXPLAIN ANALYZE before/after to confirm cost drop.

### 4. [MINOR] Duplicate-intensity comment contradicts implementation in `compute_user_taste_vector`
- **File:** backend/apps/recommendation/engine.py:1789-1797
- **Axis:** 5 (Code quality)
- **Issue:** Comment reads "Keep first-seen occurrence to avoid duplicate amplification." but the code does `intensities[bid] = max(intensities[bid], intensity)` — i.e. it promotes to the *highest* intensity, not the first-seen value. Both are defensible (max guards against accidental down-weighting from a stale low-intensity entry), but the comment is wrong about what the code does.
- **Why it matters:** Future maintainer relying on the comment may "fix" the code to actually use first-seen, silently changing taste-vector semantics across users with the same building liked twice with different intensities.
- **Suggested fix:** Update comment to: `# Use the highest intensity if the same id appears twice (e.g. across multiple Projects).`

## Optimization Opportunities
1. **Single round-trip for warm path** — `compute_user_taste_vector` does one query for `Project.values_list('liked_ids', flat=True)` then a second for `get_pool_embeddings`. Then `taste_ranked_page` does the SQL ranking. Three round-trips per request to Neon (ap-southeast-1, ~100-250 ms RTT each). Could collapse the embedding-fetch + ranking into one CTE that joins the in-memory liked_ids set against `architecture_vectors` — saves one full RTT per Discovery page-load. Not blocking; tracks well with the IMP-7/IMP-8 backlog.
2. **Memoize the user taste vector** — taste vector only changes when the user mutates a Project's `liked_ids`. A simple cache key (`f'taste:{profile.id}:{count_liked}'`) with ~5 min TTL would eliminate repeated computation across infinite-scroll pages 2..N within the same Discovery visit. Invalidate on swipe-result write or project mutation.
3. **Bulk-bookmark endpoint** — addresses both the SurpriseBoardModal orphan-board correctness issue (Finding 1) and the 10× sequential RTT cost in the same change.
4. **Shared CTE in `taste_ranked_page`** — Finding 3.

## Security Analysis
- **Auth posture:** Both new views set `permission_classes = [IsAuthenticated]`. `_get_profile(request)` returns the profile attached to `request.user`; if None (somehow authenticated user with no profile), both views return 401 explicitly rather than 500, which matches the pattern used elsewhere.
- **IDOR:** Exclusion sets are sourced from `Project.objects.filter(user=profile)` — strictly user-owned data. No path to read another user's likes.
- **SQL injection:** All inputs to `taste_ranked_page` flow through psycopg2 parameterization. `exclude_ids` is filtered to `isinstance(bid, str)` before binding to `%s::text[]`. `cursor` and `limit` are validated as integers in the view (`int(...)` cast inside try/except returning 400 on failure) and re-cast to `int(offset)`/`int(limit)` inside the engine function — defense in depth. `_vec_to_pg` formats only floats, replacing NaN/Inf with 0.0; cannot inject SQL.
- **Input validation:** `cursor < 0` and `limit ∉ [1,30]` both return 400. Missing-param case (`cursor` absent) defaults to 0 — intentional and safe.
- **Bookmark side-channel:** `bookmarkBuilding` is the existing `ProjectBookmarkView` — already auth-gated and owner-checked. SaveToBoardModal uses it correctly.
- **Frontend token usage:** `callApi` already attaches the JWT; no new code path bypasses the auth wrapper.

No security issues found.

## Part B — Browser Verification

**OVERALL: FAIL** — `/discovery` page is stuck in `loading=true` under React StrictMode dev (Vite dev server). Cards never render despite the API returning correctly.

### Evidence
- Backend `GET /api/v1/discovery/?cursor=0&limit=12` returns **200 in ~615 ms** with the expected payload: `{cards: [12 entries], next_cursor: 12, has_more: true, taste_state: "warm"}`. Confirmed via direct fetch (Test User has 378 projects, ~7 likes each — warm path is correct).
- `DiscoveryPage` renders the sticky header (`Discovery · cold`) and `LoadingSkeleton` (6 placeholder divs). It never transitions to the cards grid. After multiple reloads + SPA navigations to `/discovery`, the React state stays:
  - `loading = true` (never reset to false)
  - `cards = [] (length 0)`
  - `tasteState = 'cold'` (initial value, not the `'warm'` from the API response)
  - `isActiveRef.current = false` (sentinel that gates the response handler)
- 0 console errors, 0 console warnings, 0 4xx/5xx outside auth — the failure is silent.

### Root cause — `isActiveRef` is never reset on remount (React StrictMode-incompatible)
- **File:** frontend/src/pages/DiscoveryPage.jsx:149, 173
- **Code:**
  ```jsx
  const isActiveRef = useRef(true)
  // …
  useEffect(() => () => { isActiveRef.current = false }, [])
  ```
- Under React 18 `<StrictMode>` (enabled in `frontend/src/main.jsx:9`) in dev, mount → cleanup → remount runs on the same fiber instance, so refs are preserved. Sequence:
  1. Initial mount: `isActiveRef.current = true`. `fetchPage(0, true)` fires; `setLoading(true)`; `requestId = 1`; `await fetchDiscoveryFeed(...)` is in flight.
  2. StrictMode unmount cleanup runs → `isActiveRef.current = false`.
  3. StrictMode remount runs the `useEffect`, but the body is empty — only the cleanup is re-registered. The ref is **not** reset to `true`.
  4. ~615 ms later, the in-flight fetch resolves. The handler hits `if (!isActiveRef.current || requestId !== requestIdRef.current) return` and bails. `setCards`, `setLoading(false)`, `setTasteState`, `setHasMore` never run.
- Confirmed by walking the fiber memoizedState (16 hooks): `cards: array(len=0)`, `loading: true`, `tasteState: 'cold'`, `isActiveRef.current: false`, `requestIdRef.current: 1`.

### Production impact assessment
- **Production React 18 (no StrictMode dev double-invoke):** `useRef(true)` initializes per fresh component instance. On real navigation away → back, a new fiber + new ref are created (`current=true`), so the bug should not manifest end-to-end for users hitting a built bundle.
- **Dev / `vite dev`:** broken every time — first visit, every visit. Anyone running locally (devs, integration testers, this `/review` browser strict pass) sees an infinite loading state.
- **Vite Fast Refresh / HMR:** can also preserve refs across re-renders the same way StrictMode does, so HMR-triggered remounts in dev may exhibit the same bug.

### Required fix
Replace lines 149 + 173 with the standard "reset-on-mount" idiom so the ref is restored each time the effect runs (covering both StrictMode dev and any real-world remount where refs survive):

```jsx
useEffect(() => {
  isActiveRef.current = true   // ← reset on (re)mount
  return () => { isActiveRef.current = false }
}, [])
```

This is the canonical React 18 pattern for `isMountedRef`-style guards. Without it, the page is structurally fragile under any flow that re-runs the cleanup before the next setup body resets the ref.
