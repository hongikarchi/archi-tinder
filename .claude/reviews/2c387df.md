## Findings (Part A)

### 1. [MINOR] `currentCardRef` ref declared after the `useEffect` that captures it
- **File:** `frontend/src/App.jsx:195` (useEffect) vs `frontend/src/App.jsx:206` (useRef declaration)
- **Axis:** 5. Code quality
- **Issue:** `useEffect(() => { currentCardRef.current = currentCard }, [currentCard])` at line 195 closes over `currentCardRef`, which is not declared until line 206. JS hoisting + `useEffect` callback firing post-commit makes this work at runtime (the callback resolves `currentCardRef` after the ref-init useRef has executed), but the source reads backward and risks a reader thinking it's a TDZ bug.
- **Why it matters:** Future refactor that reorders the function body could pull the callback inline or sync, breaking the silent dependency on commit ordering. Also makes hook-rule audits harder.
- **Suggested fix:** Move `const currentCardRef = useRef(null)` to line 200 (alongside the other refs), before the new useEffect. One-line move; no behavior change.

### 2. [MINOR] Two sources of truth for "is network error"
- **File:** `frontend/src/App.jsx:35-37` (`isNetworkError`) and `frontend/src/App.jsx:44-56` (`classifySwipeError`)
- **Axis:** 5. Code quality / 2. Correctness (drift risk)
- **Issue:** Both helpers branch on the same conditions (`!status` / `err instanceof TypeError` / `message.includes('Network')`) but live in separate functions. `isNetworkError` is called in the inner-try retry (line 423); `classifySwipeError` is called in the outer catch (line 534). Drift between the two definitions would cause inconsistent classification (inner retry says "network", outer catch says "client" or vice versa).
- **Why it matters:** F2's correctness depends on both classifiers agreeing on what's transient. If one diverges, the outer setTimeout-retry path could fire on a non-transient error (or skip a transient one).
- **Suggested fix:** Express `isNetworkError(err)` as `classifySwipeError(err).kind === 'network'` (one-line wrapper) — single source of classification.

### 3. [MINOR] F4 cancel path leaves a visual gap on mouse-drag (key-remount only)
- **File:** `frontend/src/pages/SwipePage.jsx:282-294` (`onTinderSwipe`) + `328-335` (`handleDismissCancel`)
- **Axis:** 5. Code quality / UX nuance
- **Issue:** When the user drags the card left past TinderCard's threshold (120px), TinderCard internally fires `onSwipe('left')`, which sets `showDismissConfirm(true)` and animates the card off-screen. On cancel, `setLocalResetTick(t => t + 1)` increments the TinderCard `key`, forcing a remount with the card re-centered. Between the drag-release and the popup-cancel click, the card has visibly left the viewport — user sees a flicker (card flies off → blank → popup → card snaps back). The keyboard path (`swipeManual('left')` line 306-310) short-circuits before triggering the off-screen animation and is clean.
- **Why it matters:** Cosmetic UX glitch on the most common F4 trigger (drag, not keyboard). Not a correctness bug — final state is identical.
- **Suggested fix:** Either (a) pull the card back via `cardRef.current.swipe(...)` reverse animation on cancel, or (b) intercept the drag pre-threshold (use `onCardLeftScreen` only as a fallback) so popup shows while card is still centered. Optional; ship-as-is acceptable for v1.

### 4. [MINOR] Stale closure window in setTimeout retry (mitigated, not eliminated)
- **File:** `frontend/src/App.jsx:545-553`
- **Axis:** 2. Correctness (race window)
- **Issue:** `setTimeout(() => { ... handleSwipeCard(action) }, 1500)` captures the rendering's `handleSwipeCard` instance. If the user navigates away from `/swipe`, switches projects, or the session ends during the 1500 ms wait, the retry runs against stale closure state (old `currentCard`, `projects`, `activeProjectId`). The `currentCardRef.current?.image_id === retryCardId` guard catches the common case (card advanced) but does not catch project-switch or session-end during the wait.
- **Why it matters:** Edge-case correctness — retry could swipe against a project the user has just left. Real-world probability is low (1.5 s is a short window and the project-switch flow is multi-tap).
- **Suggested fix:** Add a second guard: `if (!projects.find(p => p.id === activeProjectId)?.sessionId) return` inside the timeout. Or hold a ref to `activeProjectIdRef` and compare. Optional hardening.

### 5. [MINOR] `ExitConfirmPopup` + `DismissConfirmPopup` lack dialog ARIA semantics
- **File:** `frontend/src/pages/SwipePage.jsx:112-189` + `192-258`
- **Axis:** 4. Security in depth (accessibility surface — keyboard + screen-reader users) / 5. Code quality
- **Issue:** Neither popup sets `role="dialog"`, `aria-modal="true"`, or `aria-labelledby` (pointing at the `<h2>`). Focus is not trapped inside the popup, and the `Escape` key does not dismiss it (only the cancel button + backdrop click).
- **Why it matters:** Screen reader users hear the underlying SwipePage as still in the focusable tree. Keyboard users tabbing past the popup land back in the card / TabBar. `keydown` listener on App for swipe keys is gated by `showExitConfirm/showDismissConfirm` (line 347) so Arrow keys are correctly ignored, but Tab is not trapped.
- **Suggested fix:** Add `role="dialog" aria-modal="true" aria-labelledby="..."` to the inner card div; bind Escape to onCancel via a useEffect; auto-focus the primary action button on mount.
