### 1. [MINOR] Non-transactional bulk-bookmark in SurpriseBoardModal can leave an orphan board *(carry-over, unchanged since `11c786b`)*
- **File:** frontend/src/components/SurpriseBoardModal.jsx:54-69
- **Axis:** 2 (Correctness)
- **Issue:** `handleSaveBoard` POSTs `/projects/` to create the board, then runs `for i…cards` calling `bookmarkBuilding` sequentially. If any bookmark call rejects (network blip, 5xx, partial 4xx), the catch sets `phase='error'` and the board persists with 0–N saved buildings. The `handleRetry` path only re-fetches the surprise pool — there is no compensating delete and no retry of the partially-saved board.
- **Why it matters:** 10 sequential RTTs to a JWT-auth Neon route — failure probability non-trivial. User ends up with phantom boards in `/profile`.
- **Suggested fix:** bulk-bookmark endpoint (`POST /projects/{id}/bookmarks/bulk/` with idempotency on building_id) OR compensating `DELETE /projects/{id}/` on loop failure. Out of scope for S7; S8 candidate.

### 2. [MINOR] Exclusion-set construction duplicated across DiscoveryFeedView + BoardSurpriseView *(carry-over)*
- **File:** backend/apps/recommendation/views/discovery.py:46-66 and 115-135
- **Axis:** 5 (Code quality) / 7 (Cross-commit drift)
- **Issue:** Two views contain identical 21-line blocks fetching `Project.objects.filter(user=profile).values('liked_ids','disliked_ids','saved_ids')`, deduping across types, returning both ordered list + set.
- **Why it matters:** Any future change to exclusion semantics (e.g. `disliked_ids` shape evolves) must be applied twice.
- **Suggested fix:** Extract `_collect_user_exclusions(profile) -> tuple[list[str], set[str]]` into `views/_shared.py`.

### 3. [MINOR] `taste_ranked_page` computes pgvector distance twice per row *(carry-over)*
- **File:** backend/apps/recommendation/engine.py:1830-1845
- **Axis:** 3 (Performance)
- **Issue:** CTE selects `embedding <=> %s::vector AS score` and `ORDER BY embedding <=> %s::vector ASC` repeats the expression. Two distance computations per candidate row; planner may not collapse them because the two literals are bound as separate parameters.
- **Why it matters:** Discovery feed is the new home tab — every page-load + infinite-scroll fetch hits this. With ~25k rows in `architecture_vectors`, a 30% computed-twice penalty matters.
- **Suggested fix:** Reuse the alias: `ORDER BY score ASC` inside the CTE; drop the second `%s::vector` placeholder + `_vec_to_pg(v_taste)` param. EXPLAIN ANALYZE before/after.

### 4. [MINOR] Duplicate-intensity comment contradicts implementation in `compute_user_taste_vector` *(carry-over)*
- **File:** backend/apps/recommendation/engine.py:1789-1797
- **Axis:** 5 (Code quality)
- **Issue:** Comment "Keep first-seen occurrence to avoid duplicate amplification." but code does `intensities[bid] = max(intensities[bid], intensity)` — promotes to highest intensity, not first-seen.
- **Why it matters:** Future maintainer relying on the comment may "fix" the code to actually use first-seen, silently changing taste-vector semantics.
- **Suggested fix:** `# Use the highest intensity if the same id appears twice (e.g. across multiple Projects).`

### Why downstream gates were env-blocked (and why this is not an S7 regression)
- The frontend `SaveToBoardModal` runs `listProjects()` in its mount effect. With Test User's 378 projects, the backend `ProjectListCreateView` (which fetches with the default `ProjectSerializer` including nested user object) takes ~8.5 s — confirmed via direct curl: `time:8.449s`.
- React 18 `<StrictMode>` (enabled in `frontend/src/main.jsx:9`) double-invokes effects in dev. Both modal mounts fire `listProjects()`. The first call returns 200 (cached by the browser) but its setState is skipped because the closure's `cancelled` flag is true. The second call runs against the same slow endpoint; with concurrent Neon serialization the second wall time can exceed the 10 s `FETCH_TIMEOUT_MS` ceiling, raising `AbortError` and surfacing as `[api/client] listProjects failed: AbortError`. The board list never reaches `setBoards`, so the user can't pick a board to save.
- Path conditions: (a) **production** bundle does NOT double-mount → single 8.5 s fetch → 200 → boards render → flow works; (b) **dev with a normal-sized account** → single dev double-mount fits within 2× 8.5 s budget → flow works; (c) **dev with Test User** → second fetch trips the 10 s timeout.
- Neither (b) nor (c) is on the S7 commit path: `SaveToBoardModal.jsx` has not changed since `11c786b` (the original S7 feature commit). The interaction is between (i) Test User's data accumulation across many `/review` cycles, (ii) the pre-existing `ProjectListCreateView` latency on large accounts, and (iii) the global 10 s fetch timeout. None of those three things were touched by `0ee6b42`.

### Side-observation (out of S7 scope; suggested follow-up)
The slow-listProjects + StrictMode-double-mount + global-timeout interaction is a real (if narrow) DX issue that will affect any future page mounting `listProjects` in a `<StrictMode>` shell for an account with many projects. Two cheap fixes are candidates for a separate ticket, neither S7-blocking:
1. **Server-side**: add `select_related('user')` (or the equivalent) on `Project.objects.filter(user=profile)` in `ProjectListCreateView.get` to defang the N+1 in `ProjectSerializer`'s nested user expansion. Should drop list-50 latency from ~8.5 s to <500 ms.
2. **Client-side**: switch `SaveToBoardModal`'s `useEffect` to a `useState`-cached fetcher (or a shared `useProjects()` hook with module-level cache) so the dev-mode StrictMode remount reuses the first call's result rather than firing a parallel second call.

These are **observations**, not S7 regressions. Filing them as MINOR notes here is sufficient — no blocking action.
