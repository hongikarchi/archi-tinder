## Findings (Part A)

### 1. [MINOR] Dead diagnostic instrumentation in App.jsx + DebugOverlay.jsx
- **Files:** `frontend/src/App.jsx:181-182,343-359,506-512` and `frontend/src/components/DebugOverlay.jsx:27,65-141` and `frontend/src/layouts/MainLayout.jsx:96-108`
- **Axis:** 5 (Code quality) + 7 (Cross-commit drift)
- **Issue:** `App.jsx` keeps `swipeLog`/`swipeCount` refs that get populated with `_dbg` entries on every swipe (~12 fields × every swipe, capped at 10 entries) but nothing consumes them. `DebugOverlay.jsx` accepts a `swipeDebug` prop and renders an entire QUEUE + SWIPE LOG section when it is truthy, but `MainLayout.jsx:97` invokes `<DebugOverlay userId session ...>` with no `swipeDebug` prop. The 8f783d1 commit message explicitly says "drop unused swipeDebug prop pass in MainLayout.jsx (App.jsx aggregation dropped during conflict resolution)" — the wiring was deliberately removed but the producer-side code in App.jsx and consumer-side code in DebugOverlay.jsx still ships.
- **Why it matters:** Dead-code maintenance cost; readers see `swipeLog.current.push(_dbg)` in App.jsx and reasonably ask where it surfaces. Also a small allocation cost per swipe (the `_dbg` object stays alive for the life of the swipe ref window). No behavior bug.
- **Suggested fix:** Either (a) rewire by passing `swipeDebug={{ log: swipeLog, swipeLock, imagePreloadCache, currentCard, prefetchCard, prefetchCard2, isSwipeLoading }}` from App.jsx → MainLayout → DebugOverlay; or (b) delete `swipeLog`/`swipeCount` + the `_dbg` machinery in App.jsx and the queue/log section in DebugOverlay.jsx. Pick one; do not ship both halves disconnected.

### 2. [MINOR] `getBoardBuildings` missing 200-item chunking
- **File:** `frontend/src/api/projects.js:83-93`
- **Axis:** 2 (Correctness)
- **Issue:** `getBuildings` (line 61) now chunks the `building_ids` list into batches of 200 because `BuildingBatchView.post` rejects `len(ids) > 200` with a 400 (`backend/apps/recommendation/views/swipe.py:167-168`). The sibling `getBoardBuildings` (line 83) uses the same endpoint with no chunking. Boards with > 200 saved buildings will hit the 400 path silently (caught, logs to console, returns `[]`).
- **Why it matters:** Today boards rarely exceed 200; will become a silent failure mode if any user accumulates a large saved set.
- **Suggested fix:** Apply the same chunk-of-200 + `Promise.all` pattern to `getBoardBuildings`. Trivial copy-paste of the loop from `getBuildings`.

### 3. [MINOR] `preloadImage` lost its 1500 ms ceiling
- **File:** `frontend/src/App.jsx:200-210` (compare with diff context)
- **Axis:** 3 (Performance) + 2 (Correctness)
- **Issue:** Old code resolved the promise after 1500 ms regardless of image load. New code resolves only on `img.onload` or `img.onerror`. Non-instant swipe path now `await`s the image (`App.jsx:475-477`), so a slow CDN response keeps the swipe blocked on `setCurrentCard` until the browser's own image-fetch timeout (~60-90 s) or `onerror` fires.
- **Why it matters:** Deliberate per the "블랭크 스크린 수정" intent (commit 1d026f6) — the fix prevents a half-loaded card flashing in. Acceptable when most images load fast; pathological CDN stalls become user-visible "frozen on swipe".
- **Suggested fix:** Reintroduce a longer ceiling (e.g. `setTimeout(resolve, 5000)`) so the worst case bounds at 5 s instead of browser default. Optional; not blocking.

### 4. [MINOR] Duplicate intensity-coercion logic in swipe.py
- **File:** `backend/apps/recommendation/views/swipe.py:461-466` and `:743-749`
- **Axis:** 5 (Code quality)
- **Issue:** Intensity is parsed and clamped to [0.0, 2.0] inside the `action == 'like'` branch (line 461-466) to write to `project.liked_ids`, then re-parsed identically (line 743-749) for the telemetry payload. Both copies should yield the same value, but they are independently maintained.
- **Why it matters:** Drift risk on a future tweak — one copy could move (e.g. clamp range) while the other lags. Single source-of-truth is cleaner.
- **Suggested fix:** Compute `_intensity` once near the top of the swipe processing block (after action validation) and reuse in both the `like` branch and the telemetry kwargs.

### 5. [MINOR] `SessionStateView` still uses sequential `get_building_card`
- **File:** `backend/apps/recommendation/views/sessions.py:271,290,296,313,319`
- **Axis:** 3 (Performance)
- **Issue:** `SessionCreateView` was updated to use `get_buildings_by_ids(initial_batch[:3])` (1 RTT for 3 cards). `SwipeView` was updated to use `get_buildings_by_ids([next_bid, pf_bid, pf2_bid])` in sync path (1 RTT for 3 cards). `SessionStateView` (the page-refresh resume path) still issues 3 separate `get_building_card` calls (`current`, `prefetch`, `prefetch_2`). Each is now cache-aware, so warm cache absorbs this, but cold-state refresh costs 3 RTTs.
- **Why it matters:** Refresh is low-frequency, but the optimization pattern is now applied unevenly across views. Easy consistency win.
- **Suggested fix:** Collect `[current_bid, pf_bid, pf2_bid]` (skipping `None`) and call `get_buildings_by_ids` once, then route by ID into the response fields.

### 6. [MINOR] No test coverage for cache-aware `get_buildings_by_ids` semantics
- **File:** `backend/apps/recommendation/engine.py:388-430` (new caching logic) — no corresponding test
- **Axis:** 6 (Test coverage)
- **Issue:** `get_buildings_by_ids` now does cache-lookup-then-DB-fetch-only-misses-then-preserve-order. `tests/test_imp7_pool_cache.py` covers the embedding cache and `tests/conftest.py` mocks `get_buildings_by_ids` autouse, but no test asserts: (a) cache hits short-circuit the DB call, (b) only misses are SELECT'd, (c) output order matches input order even when half is cached.
- **Why it matters:** The cache logic is straightforward but the order-preservation guarantee is load-bearing (frontend renders `next_image / prefetch_image / prefetch_image_2` from positional indices in `_initial_cards`). A regression here would silently reshuffle the initial card sequence.
- **Suggested fix:** Add a targeted test in `tests/test_imp7_pool_cache.py`: prime the cache for half of an input list, call `get_buildings_by_ids`, assert DB was called once with only the uncached IDs and output order matches the input list. Cursor-monkey-patch pattern already established in that file.

## Optimization Opportunities
- Vectorized MMR (`engine.py:1340-1369`) replaces Python double-loop with numpy matmul. At N≈150 pool × M≈30 exposed × K∈{1,2} centroids, expected speedup ~30-60× per swipe. Significant.
- Per-card cache (`get_building_card`, `get_buildings_by_ids`) on top of LocMemCache. With pool size 150 + warm cache, most card lookups become memory hits. Saves ~50-150 ms per swipe on Neon (US→EU RTT).
- Async telemetry thread moves ~4 DB round-trips (~1.2 s aggregate per swipe payload) off the response path. Significant user-felt latency win.
- `getBuildings` chunk-of-200 + `Promise.all` is well-formed; if both chunks fail one rejects → catch returns `[]`. Could be tightened to `Promise.allSettled` to salvage partial results — currently rare-enough not worth doing.
- **Future**: SessionStateView batch-fetch (finding #5) and `getBoardBuildings` chunking (finding #2) are obvious consistency wins.
