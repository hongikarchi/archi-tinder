## Findings (Part A)

### 1. [MINOR] `galleryFilter` state persists across in-app building navigation (theoretical)
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:252`
- **Axis:** 2. Correctness & logic depth
- **Issue:** `const [galleryFilter, setGalleryFilter] = useState('all')` initializes
  once. React Router keeps the same component instance mounted when only the
  `:buildingId` route param changes, so the filter selection survives. Edge case:
  user is on Building A in "Drawings" filter → in-app navigation jumps to
  Building B with zero drawings → Photos section hidden (`galleryFilter !== 'drawings'`
  is false) AND Drawings section hidden (`drawings.length === 0`). Result: blank
  gallery area while photos exist.
- **Why it matters:** User confusion + perceived breakage. In *current* app code there
  is no internal `<Link>` from one BuildingDetailPage to another (all entry
  points are `ResultsPage` / `BoardDetailPage` / `ProjectCard`, all of which
  unmount the detail page), so this is **code-read only — not reproduced in
  the current navigation flow**. Browser repro attempted via cross-building
  full-page nav (page.goto), which resets state and so cannot exercise the
  bug. The concern lands when a future "related buildings" / "next building"
  in-app link is added.
- **Suggested fix:** `useEffect(() => setGalleryFilter('all'), [buildingId])` —
  one line; pre-empts the issue before any in-app link ships.

### 2. [MINOR] Per-image badge style duplicated literally between Photos and Drawings sections
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:403-416, 455-468`
- **Axis:** 5. Code quality
- **Issue:** The 13-line absolute-positioned `<span>` badge (background rgba,
  fontSize 10, padding 2px 6px, etc.) is repeated verbatim in both masonry
  sections. The two `<section>` wrappers, h2 styling, and masonry container
  are also near-identical (Drawings sets `background: '#fff'` and
  `objectFit: 'contain'` — those two lines are the only real diff).
- **Why it matters:** Future style tweaks (e.g. badge font size for
  accessibility) need edits in two places, risk of drift. Maintainability nit;
  not blocking.
- **Suggested fix:** Extract `<KindBadge kind={kind} />` or hoist the badge
  style to a module-level constant. Optionally extract
  `<MasonrySection items label variant='photos' | 'drawings' />` — ~80 LOC
  reduction.

### 3. [MINOR] Inconsistent eager-loading between Photos and Drawings sections
- **File:** `frontend/src/pages/BuildingDetailPage.jsx:396, 447`
- **Axis:** 3. Performance & optimization
- **Issue:** Photos use `loading={idx < 2 ? 'eager' : 'lazy'}` so the first 2
  are eager-loaded. Drawings use `loading="lazy"` unconditionally. When the
  user filters "Drawings", no drawings are eager-loaded even though they are
  above-the-fold.
- **Why it matters:** Brief blank-image flash on filter switch to "Drawings".
  Minor UX inconsistency.
- **Suggested fix:** Apply the same `idx < 2 ? 'eager' : 'lazy'` pattern to
  drawings, or unify to one consistent rule documented in a comment.

## Optimization Opportunities

- Per-building API: single `POST /images/batch/` with 1 ID, ~632 ms
  observed (auth + DB + JSON). Reasonable for a detail page. A dedicated
  `GET /buildings/<id>/` (cacheable) could shave latency but is premature.
- 67 lazy images on bld_025688 — browser handles `loading="lazy"`
  natively, no perf issue.
- No prefetch hint for likely-next building (e.g. when entering from
  ResultsPage top-K). Out of P4 scope.

## Security Analysis

- `gallery_meta` carries `{url, kind}` only; both sourced from
  `canonical_v2_buildings.all_images` (Make-DB-curated, not user input).
  No new injection vector vs the existing `gallery` URL array.
- Frontend renders `kindLabel(item.kind)` which dict-maps to a fixed label
  set → unknown kind falls through to `'Photo'`. URL goes into
  `<img src={item.url}>` — React auto-escapes attribute values;
  `javascript:` / `data:` schemes don't execute in modern `<img src>`.
- `BUILDING_ID_RE = /^[A-Za-z0-9_-]{1,32}$/` defense-in-depth pattern
  check before API call (mirrors `FirmProfilePage` pattern). Invalid
  pattern early-exits to error state.
- Bookmark POST gated on `fromProjectId && rank && !bookmarkPending`;
  `isValidRank` clamps rank to [1, 100]. Backend ownership filter
  unchanged.
- No auth / token flow touched. No new endpoints.
