## Findings (Part A)

### 1. [MINOR] Silent revert on PATCH/DELETE failure — no user-visible feedback
- **File:** `frontend/src/pages/UserProfilePage.jsx:149-158, 161-173`
- **Axis:** 2. Correctness & logic depth / 5. Code quality
- **Issue:** When `updateProject` or `deleteProject` throws (network /
  403 / 5xx), the optimistic state is reverted and the error is logged to
  `console.error` only. User sees their action visually undo with no toast,
  banner, or aria-live announcement — looks like a flicker / phantom bug
  rather than a server failure.
- **Why it matters:** Failure modes most likely to fire here (403 if
  session expired, 5xx during Neon hiccup, network drop on mobile) need
  user guidance. Compare `App.jsx:546` swipe error toast pattern which
  classifies and surfaces network/server/client errors. P5 owner edits
  warrant equivalent treatment.
- **Suggested fix:** Reuse the `swipeError` toast pattern or add a
  `boardActionError` state surfaced as a small toast above the boards
  grid. Out-of-scope for this PR if treated as P5.1 follow-up.

### 2. [MINOR] handleDelete snapshot revert can drop concurrently-paginated boards
- **File:** `frontend/src/pages/UserProfilePage.jsx:161-173`
- **Axis:** 2. Correctness & logic depth
- **Issue:** `const snapshot = boards` captures the array at callback
  entry. If `loadMoreBoards` (IntersectionObserver-triggered) appends new
  boards while the DELETE request is in flight, and the DELETE then fails,
  `setBoards(snapshot)` restores the pre-pagination state and drops the
  newly-loaded boards. Same race on `boardsTotalCount`. Window is small
  (~ms-sec); realistic only if user scrolls to sentinel right after
  clicking X.
- **Why it matters:** Boards visually disappear from the grid until next
  scroll/refresh. Theoretical race, not reproducible in normal flow.
- **Suggested fix:** Revert by id rather than snapshot —
  `setBoards(bs => [deletedBoard, ...bs.filter(b => b.board_id !== boardId)])`
  using a `deletedBoard = boards.find(...)` capture, and decrement total
  via functional updater that already exists. Preserves any
  concurrently-loaded boards.

### 3. [MINOR] Rapid double-toggle of visibility can persist with stale `prev`
- **File:** `frontend/src/pages/UserProfilePage.jsx:149-158`
- **Axis:** 2. Correctness & logic depth
- **Issue:** `prev = boards.find(b => b.board_id === boardId)?.visibility`
  is captured at callback start. If the user clicks the lock chip twice
  quickly (toggle A→B→A) before the first PATCH resolves, both
  optimistic updates apply correctly but the second callback's `prev` is
  the optimistic intermediate state, not the true server-confirmed
  baseline. Worst case if first PATCH fails: revert sets visibility to
  the wrong value (the second toggle's optimistic value, not the original
  server value). Bounded harm: backend remains source-of-truth and next
  page load re-sync.
- **Why it matters:** Edge case — requires double-click within ~200 ms
  AND first PATCH failure. Low-likelihood, low-impact.
- **Suggested fix:** Lock per-board during pending PATCH (mirror
  `isFollowingPending` pattern in the same file), or capture
  server-confirmed visibility from the most recent PATCH response.

## Optimization Opportunities

- `useCallback(handleDelete, [boards, boardsTotalCount])` rebuilds on
  every boards mutation, which causes every `BoardCard`'s `onDelete`
  closure to be a new identity each render. Irrelevant at ~12 boards;
  worth noting if board grid scales beyond 100.
- BoardCard's `useEffect(handleOutsideClick)` attaches a mousedown
  listener whenever `confirmingDelete` is true. Per-card listener is
  fine; if many simultaneous confirmations were possible (they aren't —
  single confirm at a time per card) you'd consolidate at the document
  level.
- The 2 SVG variants (lock-closed / lock-open) could collapse into one
  shared `<svg>` with a conditional `<path>` — strictly cosmetic.

## Security Analysis

- `ProjectDetailView.patch/delete` owner-only via `project.user_id != profile.pk`
  → 403; unauthenticated → 401. Both observed in
  `backend/apps/recommendation/views/projects.py:77-99`. Correct.
- `ProjectSelfUpdateSerializer` restricts PATCH `fields` to
  `['name', 'visibility']` — visibility-only attack surface for the new
  toggle, name unchanged. Privilege-escalation impossible via this
  endpoint.
- Frontend `isOwner={isMe}` derives from
  `String(routeUserId) === String(sessionUserId)` — only own-profile path
  shows mutation chips. Bypassing via dev tools still fails at backend
  owner check.
- `effectiveUserId` defense-in-depth regex `/^\d+$/` (line 32) — path
  traversal mitigated.
- No new endpoints; no new state in localStorage / cookies. No CSRF
  posture change (DRF stateless JWT).
- `Confirm?` text is a literal string — no XSS surface. Lock SVG attributes
  are static.
- No tokens / secrets / PII handled by this diff.
