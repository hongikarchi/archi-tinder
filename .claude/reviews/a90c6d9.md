## Findings (Part A)

### 1. [MAJOR] `gh pr checks` exit-code mapping reversed in `git-poll-merge.sh`
- **File:** `tools/git-poll-merge.sh:42-75`
- **Axis:** 2 (correctness)
- **Issue:** Script comment claims `gh pr checks exits 0=pass, 8=fail, 1=running`
  and case-maps accordingly. GitHub CLI's documented and source-confirmed behavior
  is the opposite for the failure/pending split: **exit 0 = all pass, exit 1 = at
  least one failed (`SilentError`), exit 8 = some still pending (`PendingError`)**.
  The current script therefore:
  - Treats `gh` exit 8 (pending) as `CHECKS FAILED` → emits a false `PR-CI-FAIL`
    handoff while CI is still running.
  - Treats `gh` exit 1 (failed) as `still pending` → polls until 10-minute timeout
    and emits `PR-CI-TIMEOUT` for what is actually a failed run.
- **Why it matters:** WEB-GIT Mode 1 step 4 depends on this script for the
  `PR-CI-GREEN` / `PR-CI-FAIL` handoffs. With the mapping reversed, the operator
  receives systematically wrong CI signals on the very first PR that uses this
  workflow, and a real CI failure won't fire the FAIL handoff (it'll silently age
  out as TIMEOUT).
- **Suggested fix:**
  ```bash
  case "$CODE" in
      0) ... GREEN ... exit 0 ;;
      8) ... still pending ... ;;          # was 1
      1) ... CHECKS FAILED ... exit 1 ;;   # was 8
      *) ... unexpected ... ;;
  esac
  ```
  Update the inline comment to match. Empirically verify against the operator's
  installed `gh` version with a known-failing PR before relying on it. (Older
  gh versions overload exit 1 for both fail and pending — the safer fallback is
  to scan `OUTPUT` for `fail`/`error` keywords on any non-zero exit.)

### 2. [MAJOR] `git branch -d feature/<branch>` will refuse to delete after squash-merge
- **File:** `.claude/agents/git-publisher.md:79-86` (Mode 1 step 7)
- **Axis:** 2 (correctness) / 5 (code quality, instruction accuracy)
- **Issue:** Step 7 prescribes:
  ```bash
  git checkout develop && git pull origin develop
  git branch -d feature/<branch>     # already merged, safe to delete locally
  ```
  After `gh pr merge --squash --delete-branch`, the squash creates a *new* commit
  on `origin/develop`; the original feature-branch commits are NOT ancestors of
  develop's HEAD. `gh pr merge --delete-branch` deletes the *remote* feature
  branch, which also drops the local branch's upstream. With no upstream, `git
  branch -d` falls back to checking HEAD (now develop) for ancestry — and since
  the feature commits aren't reachable from develop, it errors with "branch
  feature/<branch> is not fully merged."
- **Why it matters:** Every internal Mode 1 PR will hit this on cleanup. Operator
  has to manually use `-D` (or rebase first) and the prescribed flow is wrong.
  The "safe to delete locally" comment misleads about the actual git semantics.
- **Suggested fix:** Two options, prefer (a):
  - (a) After confirming `gh pr view <N> --json state` reports `MERGED`, use
    `git branch -D feature/<branch>` and document why (squash creates a new
    commit; original feature-branch tip is no longer reachable from develop).
  - (b) Keep `-d` but precede with `git fetch --prune origin && git config
    --add branch.feature/<branch>.merged true` — clunkier and not idiomatic.
  Mirror the same fix in `tools/git-poll-merge.sh` "Append to ... PR-MERGED:"
  guidance so script and agent stay aligned.

### 4. [MINOR] Mode 2 step 6 hardcodes `pr-<N>` despite the immediately-following note
- **File:** `.claude/agents/git-publisher.md:174-180`
- **Axis:** 5 (code quality, instruction internal consistency)
- **Issue:** Step 6 reads:
  ```bash
  git checkout develop
  git branch -D pr-<N>
  ```
  but the very next "Important" callout correctly notes that
  `gh pr checkout <N>` names the local branch after the PR's head ref name (e.g.
  `feature/algo-mmr-tuning`), not `pr-<N>`. The step body and the warning
  contradict each other in the same agent's instruction set; an agent reading
  top-down will execute the wrong delete.
- **Why it matters:** WEB-GIT may delete a wrong branch or, more likely, fail
  with "branch pr-12 not found" while the actual head-ref branch lingers.
- **Suggested fix:** Replace step 6's body with `git branch -v` discovery first,
  then `git branch -D <discovered-ref>`; or fold the callout's instruction into
  the step itself.

### 5. [MINOR] No automated/dry-run check for any of the new tool wrappers

### 6. [MINOR] `git-stage-and-commit.sh` post-commit file-count fallback edge cases
- **File:** `tools/git-stage-and-commit.sh:105`
- **Axis:** 5 (code quality)
- **Issue:**
  ```bash
  COUNT=$(git diff --cached HEAD~1 --name-only 2>/dev/null | wc -l | tr -d ' ' || echo "?")
  ```
  - On the first commit ever in a repo, `HEAD~1` doesn't exist; `git diff` errors
    silently (stderr suppressed); `wc -l` reads empty input → `0`. So COUNT is
    `0`, not `?` as the `|| echo "?"` clause suggests.
  - The unquoted `$(echo "$staged" | grep ...)` in line 77's `git reset HEAD --`
    splits on whitespace; a filename with spaces would unstage the wrong path. In
    practice we never commit secret files with spaces, but the fallback is
    fragile.
- **Why it matters:** Cosmetic in normal flow. The line-77 issue is in an error
  path we already abort from (`exit 5`), so the bad `git reset` is best-effort
  cleanup, not load-bearing.
- **Suggested fix:** Use `git diff-tree --no-commit-id --name-only -r HEAD | wc -l`
  for accurate just-committed file count, and use a `while IFS= read -r line; do
  git reset HEAD -- "$line"; done` pattern in line 77 if we keep the cleanup.

## Optimization Opportunities

- `front-validate.sh` runs `npm run lint` then `npm run build` sequentially. Parallel
  would shave ~10s but breaks fail-fast clarity. Stay sequential.
- `back-validate.sh` chains flake8 → migrate-if-needed → pytest. Migration sub-step
  could short-circuit by checking `git diff --quiet -- 'backend/apps/*/migrations/*.py'`
  rather than building a string and grepping; cosmetic.
- `dispatch.sh` long-message (>1500 char) fallback writes to `/tmp/dispatch-<team>-*.md`
  with no auto-cleanup. Files accumulate over time. Add a `find /tmp -name 'dispatch-*'
  -mtime +7 -delete` opportunistically, or move to a managed directory. (Out of scope
  for this commit; flag as cleanup task.)
- `cleanup-after-push.sh` sleeps `sleep 4` after `/clear`; if cmux's send returns
  before the agent's input prompt is ready, the init message lands in a buffer
  that gets cleared. Empirical 4 s is fine but flaky on slow startup; consider
  polling a screen marker instead.

## Security Analysis

No new auth surface. No external commands executed against secrets. The diff
adds three relevant new code paths:

- **`git-stage-and-commit.sh` secret-skip pathspec**: pathspec excludes `.env`,
  `.env.*`, `__pycache__/`, `*.pyc`, `*.key`, `*.pem`, `*.p12`, `*.pfx`,
  `credentials.*`, `secrets/`. Defense-in-depth scan after staging
  (`git diff --cached --name-only | grep -E ...`) reports + aborts (exit 5)
  if a secret-pattern file slipped through. Solid layering. Note that the
  pathspec excludes `__pycache__` (no glob) but the scan regex doesn't match
  `__pycache__` — the cache exclusion is intentional (not a secret), so this is
  consistent.
- **`git-poll-merge.sh` extracts `link` from `gh pr checks --json` output** via
  `grep -o '"link":"[^"]*"' | head -1 | sed ...`. The link comes from GitHub's
  API (trusted). Unescaped substitution into a string echoed to stdout (handoff
  signal) is fine — it's not interpreted as shell.
- **`dispatch.sh` long-message fallback** writes the full message verbatim to
  `/tmp/dispatch-<team>-<ts>.md`. Plan content is not sensitive in our threat
  model (no secrets in dispatch payloads), and `/tmp` is a per-user directory
  on macOS. OK.

`git-publisher.md` hard guardrails 1–6 are explicit (never commit source, never
push to main, never `--force`, never approve own PR, never merge red CI without
operator confirmation, never modify CODEOWNERS / workflows / rulesets). These
correctly delineate the trust boundary between WEB-GIT and WEB-MAIN.
