## Findings (Part A)

### 1. [MINOR] `(db-handoff-needed)` suffix not propagated to orchestrator.md
- **File:** `.claude/agents/team-back.md:138-149` (signal definition)
- **Axis:** 7 — Cross-commit drift (documentation propagation)
- **Issue:** The commit introduces a new handoff-message suffix `(db-handoff-needed)` that WEB-BACK appends to `BACK-DONE` when codex could not run `python3 manage.py migrate` (sandbox blocks DNS to Neon). The suffix's contract is documented in `team-back.md` only. Its sibling suffix `(claude-review-requested)` is documented in three places: `AGENTS.md:47,52`, `team-back.md`, AND `orchestrator.md:216` (where the hybrid-pre-commit policy explicitly instructs the orchestrator to "DO run reviewer + security on top of the self-review" when it sees that suffix in a DONE message). No equivalent line in `orchestrator.md` tells WEB-MAIN to "apply the migration via `python3 manage.py migrate` before triggering git-manager" when it sees `(db-handoff-needed)`.
- **Why it matters:** When WEB-MAIN reads `BACK-DONE: <slug> (db-handoff-needed)` from `Task.md § Handoffs`, the orchestrator agent has no documented protocol for the suffix. It may proceed straight to git-manager and commit a migration file that never ran against Neon — precisely the failure mode the SOC3-back 2026-05-06 incident exposed. The team-back.md text relies on WEB-MAIN reading team-back.md retroactively, which is feasible but breaks the discoverability symmetry with `(claude-review-requested)`.
- **Suggested fix:** Add one bullet to `orchestrator.md` adjacent to the existing line 216 hybrid-policy bullet, e.g. "When a `BACK-DONE` handoff carries `(db-handoff-needed)`, run `cd backend && python3 manage.py migrate` (and a smoke `pytest -k <new_app>` if the migration is data-touching) before dispatching git-manager." Optionally also list the suffix in `AGENTS.md` § Handoff signals for parity with `(claude-review-requested)`. Non-blocking for push — the human at WEB-MAIN can apply migrate manually on first encounter and patch the doc on the next iteration.

## Security Analysis
Surface touched: shell tooling that types user-controlled strings into cmux workspace prompts.

- **Command injection** — the existing line 96 (`$CMUX send --workspace "$ws_ref" --surface "$surf_ref" "$flat_msg"`) passes `$flat_msg` as a quoted argv element to `cmux send`. `cmux send` is not a shell — it types the string literally into the target pane. Shell metachars in `$flat_msg` cannot escape the quoting and reach a shell on the WEB-MAIN side. The new `/clear` send on line 73 uses a literal hardcoded string (no interpolation). Safe.
- **Env-var trust boundary** — `DISPATCH_NO_CLEAR=1` is a local-dev opt-out flag. The user controls their environment; not a security boundary.
