## Observations (sub-MINOR, not flagged as findings)

1. **Unused `refresh_from_db` before 204 DELETE** (`backend/apps/social/views.py:168` — `office.refresh_from_db(fields=['follower_count'])` followed by `Response(status=status.HTTP_204_NO_CONTENT)`). DELETE returns no body, so the refreshed count is never read. One wasted DB round-trip per unfollow. Cosmetic — already noted in `e397317` commit body's "Two non-blocking cosmetic notes for follow-up." Drop the line in a follow-up commit.

2. **`FollowWriteThrottle` docstring silent on shared-scope across user+office endpoints** (`backend/apps/social/views.py:45`). The throttle is reused for `OfficeFollowView` per commit body's intentional design (60/min cap aggregating user-follow + office-follow actions per user — spam-prevention). The docstring still reads "60 follow/unfollow actions per user per minute — prevents mass-follow bots" which doesn't acknowledge the office-side aggregation. Cosmetic — already noted in commit body. Update docstring in a follow-up commit.

3. **`FirmProfilePage` officeId regex is too loose for UUIDs.** The existing regex `/^[A-Za-z0-9_-]{1,64}$/` (from `b272f37`) was originally written assuming OFF001-style IDs. Office.office_id is actually `UUIDField` (UUIDs are 36 chars, fit within 64; alphanumeric+dashes pass the regex). Backend `<uuid:>` Django route converter is the actual enforcement (verified by smoke test: `/offices/garbage-id/follow/` → 404). Defense-in-depth still works; could be tightened to UUID format like BoardDetailPage's `aedc817` regex. Cosmetic.

4. **`handleToggleFollow` rollback on error preserves `followerCount` via Math.max(0, ...) belt** (`FirmProfilePage.jsx:135-139`). Forward path uses `Math.max(0, c + (wasFollowing ? -1 : 1))`; rollback path applies the inverse `Math.max(0, c + (wasFollowing ? 1 : -1))`. Both paths floor at 0. If the original followerCount was already 0 and the optimistic +1 succeeded but the server unfollowed-then-failed (impossible by API contract), the rollback to `Math.max(0, 1 - 1) = 0` would be correct. Defense-in-depth, no edge case in current design. Cosmetic.

## Security Analysis

- **`OfficeFollowView`**:
  - `permission_classes = [IsAuthenticated]` — anonymous → 401 (verified empirically).
  - `FollowWriteThrottle (scope=follow_write, 60/min)` reused — intentional shared-scope spam defense across all follow types per commit body.
  - `get_object_or_404(Office, office_id=office_id)` — proper 404 path (verified for non-existent UUID and for non-UUID strings rejected by Django `<uuid:>` converter).
  - Profile fallback: 403 if user has no profile (admin edge case handled).
  - DELETE uses `filter().delete()` race-safe pattern — same as SOC1.
  - `get_or_create` idempotent — 201 on new, 200 on existing.
  - No IDOR — followee Office is identified by URL UUID; follower is fixed to the authenticated user's profile via `requester = getattr(request.user, 'profile', None)`. Cannot follow on behalf of another user.

- **`OfficeDetailView.is_following` injection**:
  - Auth check before DB query — anonymous and profileless requests get `false` without a DB hit.
  - DB query is filtered by both `follower=requester` AND `followee=office` — cannot leak whether someone else follows this office.

- **`OfficeFollow` model**:
  - CASCADE on both FKs — deleting a UserProfile or Office cascades to all relevant follow rows + signal decrements counters.
  - `unique_together` prevents duplicate follow rows (defense in depth alongside `get_or_create`).

- **Frontend `FirmProfilePage`**:
  - `officeId` regex (Observation 3) gates the URL before fetch.
  - `callApi` handles JWT + refresh (Bearer token in header, never in URL/console).
  - `console.error('[office-follow]', err)` — error message logged, but `err` from `callApi` doesn't include the JWT (verified pattern from prior cycles).

- **Migration 0004**:
  - AddModel only, no data migration. Reverse-safe.

No new auth surface, no token-handling change, no permissions broadening, no SQL injection vector (Django ORM throughout), no IDOR.

Clean security verdict.
