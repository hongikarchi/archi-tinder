## Findings (Part A)

### 1. [MINOR] MainLayout passthrough fix targets a backend field that no longer exists
- **File:** frontend/src/layouts/MainLayout.jsx:124
- **Axis:** 2 (Correctness — backend/frontend contract drift)
- **Issue:** The fix changes `total: sessionProgress.total` → `total: sessionProgress.total_rounds`, but `total_rounds` was removed from the backend `_progress()` payload in migration `0006_remove_total_rounds_and_scope_idempotency.py` (the field is gone from `AnalysisSession` model and never appears in `backend/apps/recommendation/views/_shared.py:33-43`). DebugOverlay still renders `round X/?` because `session.total ?? '?'` falls back to '?' when undefined.
- **Why it matters:** The commit message claims the passthrough now reads the canonical keys, but only `current_round` is real — `total_rounds` is dead. Future readers will assume the value is being plumbed correctly when it isn't.
- **Suggested fix:** Either drop the `/total` half of the DebugOverlay session line entirely (line 59 of DebugOverlay.jsx), or surface a meaningful denominator from `_progress` (`pool_size` or `pool_remaining`) and rename accordingly. Out of scope for the S4 push since this is dev-only telemetry, but worth a follow-up cleanup.

### 2. [MINOR] Optimistic `like_count` bump not reverted on error catch-block
- **File:** frontend/src/App.jsx:344-348, 456-464
- **Axis:** 2 (Correctness — error edge case)
- **Issue:** The new optimistic bump increments `sessionProgress.like_count` synchronously on the instant-swap path. The error catch-block at line 456-464 only reverts card state when `!canInstantSwap`; when `canInstantSwap === true` and the swipe POST ultimately fails (after the network-error retry at line 379), the bumped `like_count` stays in client state alongside a "Swipe failed. Please try again." toast.
- **Why it matters:** Cosmetic drift only — the next successful swipe at line 392 (`setSessionProgress({ ...result.progress, ... })`) overwrites with backend-authoritative state, and a refresh / state GET also re-sources truth. But during the drift window the user sees a progress bar that has already advanced for a swipe the server didn't accept.
- **Suggested fix:** In the `if (!canInstantSwap)` branch's mirror — extend the revert to also undo the optimistic bump:
  ```js
  if (canInstantSwap && action === 'like') {
    setSessionProgress(p => p ? { ...p, like_count: Math.max(0, (p.like_count ?? 1) - 1) } : p)
  }
  ```
  Non-blocking; the self-correcting behavior of the next swipe response is adequate for the common case.

### 3. [MINOR] Phase-transition visual flash: "탐색 중 3/3 100%" → "준비 중 0%" → "취향 안정도 X%"
- **File:** frontend/src/pages/SwipePage.jsx:309-355
- **Axis:** 2 (Correctness — UX edge case)
- **Issue:** On the swipe that triggers `exploring → analyzing` (3rd like), the optimistic bump fills the exploring bar to 100% (`Math.min(3, 3) / 3`). The backend response then arrives with `phase='analyzing'` + `confidence=null` (no clustering yet), routing the bar to the `else` branch → label "준비 중" + width 0%. The next swipe with computed confidence jumps to "취향 안정도 X%". Visible flash: 100% → 0% → X%.
- **Why it matters:** Jarring transition after the user just "unlocked" analysis. Worse than the prior code's silent label change (which was its own bug — "X / 1" gibberish — so this is still net better, but a regression vs the visual *trajectory*).
- **Suggested fix:** When `value === null && phase === 'analyzing'`, keep the bar pinned at 100% with a transient label like `'분석 중...'` rather than dropping to 0%. Or animate the transition through a held state. Not blocking; the spec doesn't define this corner.

### 4. [MINOR] Within-page language inconsistency (English JSX strings + Korean ConfidenceBar labels)
- **File:** frontend/src/pages/SwipePage.jsx:320, 321, 325, 328
- **Axis:** 5 (Code quality / UX consistency)
- **Issue:** The codebase is already bilingual (`ResultsPage.jsx`, `BuildingDetailPage.jsx` contain Korean), so adding Korean to SwipePage isn't a global regression. Within `SwipePage` itself, however, the rest of the strings remain English ("tap for details", "View Gallery", "View persona report →", "Keep exploring", "Your taste is found", "No more buildings available", "← skip · tap card · save →"). The new Korean labels read as inconsistent inside the same view.
- **Why it matters:** Either go all-English in this view or move to a centralized strings/i18n surface so the choice is explicit and consistent. Today's frontend has no i18n infra (`grep -r 'useTranslation\|i18n\|locale' frontend/src/` returns zero hits).
- **Suggested fix:** Either translate the new labels to English to match the rest of SwipePage, or defer to a future i18n pass. Non-blocking.

### 5. [MINOR] `DebugOverlay` confidence `.toFixed(3)` lacks type guard
- **File:** frontend/src/components/DebugOverlay.jsx:65
- **Axis:** 4 (Defensive correctness)
- **Issue:** The guard `session.confidence != null ? session.confidence.toFixed(3) : 'null'` only screens out `null` and `undefined`. If the backend ever returns confidence as a string (serialization quirk, JSONField edge case, etc.), `.toFixed` throws and unmounts the overlay.
- **Why it matters:** Dev-only telemetry; not a user-facing risk. Listing as MINOR because it's a one-line defensive miss in new code, not pre-existing drift.
- **Suggested fix:** `typeof session.confidence === 'number' ? session.confidence.toFixed(3) : 'null'`.

### 6. [MINOR] `can_continue` absent from `sessionProgress` during normal swipe loop
- **File:** frontend/src/App.jsx:392 (cf. lines 399-404, 491-495)
- **Axis:** 7 (Cross-commit consistency)
- **Issue:** The normal-swipe path merges only `confidence` into `sessionProgress` (line 392); the completion path (line 399-404) and extend path (line 491-495) additionally merge `can_continue`. During the ordinary swipe loop, `sessionProgress.can_continue` is `undefined`, so DebugOverlay renders '—' until the session reaches `is_analysis_completed: true`.
- **Why it matters:** Debug overlay can't surface the `can_continue` flag mid-session, only at the terminal screen. Minor observability gap; not user-facing.
- **Suggested fix:** Mirror the merge at line 392 to also include `can_continue: result.can_continue ?? null` so every state update carries the field. Trivial follow-up.

## Architecture Alignment
Aligns with `DESIGN.md` inline-style conventions (no Tailwind, hex accent `#ec4899` matches prior usage, transition timing `300ms ease` consistent with elsewhere). Frontend-only change with no backend/API contract drift — schema `_progress` payload is unchanged, and the new fields surfaced in `DebugOverlay` (`phase`, `like_count`, `confidence`, `can_continue`) are all already part of either the swipe response or the merged client-side `sessionProgress`. The unification of the confidence-bar / like-count / round-counter triple into one component cleans up a long-standing two-branch header that drifted from spec.

The choice to compute the exploring fallback bar from `Math.min(likeCount, 3) / 3` (rather than reading `min_likes_for_clustering` from a shared constant) is acceptable for now — `min_likes_for_clustering=3` is hardcoded in backend `settings.RECOMMENDATION` and unlikely to change. If it ever moves, a `progress.unlock_threshold` field would be the cleanest plumb.

## Optimization Opportunities
- `setSessionProgress(p => p ? { ...p, like_count: ... } : p)` (App.jsx:347) allocates a new object on every like. Negligible at swipe cadence (~1 Hz) and React's diffing handles it efficiently; no action needed.
- `Math.round(value * 100)` (SwipePage.jsx:318, 324) runs on every render; React's component memoization could short-circuit but the bar component is trivial — micro-optimization not warranted.
